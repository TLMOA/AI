## 🔴 目标机「verify.sh 登录 FAIL」根因：改密码没同步给自检用的文件（已修 → 第 11 版包）

**现象**（用户传 v10 重跑后）：部署 14/14 全绿，但 `verify.sh` → `[FAIL] 登录失败（检查 .deploy-secrets
里的密码是否与实际一致）`（PASS=8 FAIL=1），`smoke_test.sh` 第 2 步直接中断。

**根因**：用户此前用 `set_password.sh humi '你的新密码'` 改过密码（把示例占位符原样敲了进去）。
该脚本**只改数据库里的密码**，不碰 `config.env`/`.deploy-secrets`；而 `verify.sh`/`smoke_test.sh`
是拿 `config.env` 的 `SITE_PASS`（缺省回退 `.deploy-secrets` 的 `ADMIN_PASS`）去登录做自检的
→ 两边不一致 → 自检必然登录失败。**不是部署坏了**：服务、端口、NiFi、台账、ODBC 全绿。

**修法（已进 v11）**：
- 🆕 `deploy-kit/tools/sync_site_password.py`：把新密码写进 `config.env(SITE_PASS)` 与
  `.deploy-secrets(ADMIN_PASS)`；不回显口令、保留文件权限、键缺失则追加、**改非站点账号时自动跳过**
  （5 项单测：两文件更新/不回显/追加/边界/权限 600）
- `set_password.sh` 改完密码自动调用它（仅当 TARGET_USER == SITE_USER），失败只 warn 不中断
- `test_e2e.sh` 新增 **12.5**：断言同步成功（含特殊字符 `N3w!@#%^&|$*()`）且改别的账号不动站点密码
- e2e 15 步全过

**顺带修掉的观感问题**：断网机器上 `deploy.sh` 第 6 步 `pip install --upgrade pip` 会重试 5 次、
打出满屏 `WARNING: Retrying ... pypi.org timed out`，白等约 75 秒（v9 加过 `|| warn` 护栏所以不中断，
但很吓人）。→ 改成 `--retries 1 --timeout 5` + 输出全进 `/tmp/iot-pip.log`，终端只在失败时给一行人话。

**用户当场的手工解法（不重传也能修）**：把当前密码同步进那两个文件（python getpass 片段，见聊天记录），
或在 `config.env` 里把 `SITE_PASS` 与 `.deploy-secrets` 的 `ADMIN_PASS` 一起改成数据库里那个值。

**交付**：第 11 版三件套（`.run` 1,778,669,208 字节 / `.sha256` 82 / `部署文档.txt` 34,021）；
四步审计全过（HEADER_SYNTAX_OK、标记行=69、sha256 成功、CMP_OK、v11 指纹命中 10 处）。

📝 教训：**任何「改了某处状态」的脚本，都要检查「还有谁依赖这个状态的旧值」** ——
改数据库密码却不同步自检文件，就是典型的“改一处、坏一处”。

## 🔍 用户要「确认没别的问题了」→ 按【bug 模式】全仓扫，又抓出两个真隐患（→ 第 12 版包）

反思：之前都是「按症状修」，于是这次把已出过的 4 类 bug 当**模式**去扫同类，扫出 2 个真问题：

### 🚨 隐患 1：`deploy.sh` 的 `as_user()` 里有**死递归**
```bash
elif command -v sudo >/dev/null 2>&1; then
  as_user "$@"        # ← 调用自己！应为 sudo -u "$APP_USER" -- "$@"
```
- 影响：有 `runuser` 的机器（Ubuntu 都自带）走第一分支，**看不出来**；一旦机器没有 runuser
  （精简安装/容器/非 Ubuntu）→ 无限递归 → 部署卡死。
- 根因：这段逻辑在 **4 个脚本里各抄了一份**，漂移出来的。另外 3 份（`verify.sh`/`set_password.sh`/
  `add_factory.sh`）写死 `sudo -u "$APP_USER"` → **没装 sudo 的机器直接失败**。
- 修法：新建 **`tools/lib.sh`** 作为唯一定义（`EUID==0` 才用 runuser → sudo → su 三级回退），
  4 个脚本统一 `source`；e2e 加静态断言（除 lib.sh 外不得出现 `sudo -u "$APP_USER"`；lib.sh 不得自递归）。
- 实测：root→runuser ✓、非 root→走 sudo ✓、无任何工具→快速报错不死循环 ✓、APP_USER 未设→明确报错 ✓。

### 🧩 隐患 2：改密码只同步了 2 个文件，`override.conf` 里的旧口令留在 /etc
`/etc/systemd/system/iot-backend.service.d/override.conf` 有 `Environment=IOT_ADMIN_PASSWORD=<旧口令>`。
虽然该值只被「未打禁止默认 admin 补丁」的场景用到（改动不影响运行），但旧口令以明文长期留在 /etc 不干净。
→ `sync_site_password.py` 支持 `--override-conf`，`set_password.sh` 自动带上（文件不存在则优雅跳过）。

### e2e 扩到 **79 项断言**
新增 12.5（同步工具 5 项：特殊字符/边界/override/权限/不回显）、12.6（**真跑** set_password.sh：
改密码→新密码能登录+文件已同步+不回显+改回幂等）、12.7（as_user 静态防复发 2 项）。
⚠️ 12.6 第一版**假失败**：容器里运行用户 `yhz` 到第 13 步才创建，而 `set_password.sh` 会 `as_user` 切到它
→ `runuser: user yhz does not exist`。**新写断言要连夹具一起想**（已在 12.6 里补 `useradd`）。
