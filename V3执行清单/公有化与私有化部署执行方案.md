# 公有化与私有化部署执行方案

**版本：v3.3**
**日期：2026-06-03**
**基于文档：**《AI模块综合执行方案（融合NiFi、联邦学习与双模部署）》

## 一、需求定义

### 1.1 公有化部署
工厂把通过我们网站规整好的训练数据，直接存放到**我们的 Ceph** 里。数据在我们自己的机器上，可以直接用于中心训练。

### 1.2 私有化部署
工厂把通过我们网站规整好的训练数据，存放在**工厂自己的 Ceph** 里。管理员通过内部管理页面切换用户并拉取数据到我们机器，再用于中心训练。

### 1.3 用户与工厂关系
每个用户就是一个工厂，用户名即工厂标识。一个工厂的 Ceph 上只有该工厂自己的数据，不存在多用户并存。

### 1.4 管理员权限
管理员登录内部管理页后，可通过顶部下拉菜单切换任意用户（公有化+私有化），查看该用户的 `nifi-data` 和 `real_nifi_data` 文件列表并执行拉取操作。

### 1.5 普通用户权限
普通用户（非管理员）登录后，在自己的"文件中心"页面可看到自己的 `nifi-data` 和 `real_nifi_data`，无论公有化还是私有化。**普通用户看不到内部管理页**。

## 二、核心数据流

```
工厂用户登录 → 配置数据库连接 → 创建导出任务
    → NiFi / Local 执行器处理 → 产出文件
              │
    ┌─────────┴─────────┐
    ▼                   ▼
【公有化用户】      【私有化用户】
    │                   │
    ▼                   ▼
 我们的 Ceph          工厂自己的 Ceph
/home/yhz/in-data/    {ceph_endpoint}/
  {username}/            ├── nifi-data/
    ├── nifi-data/       └── real_nifi_data/
    └── real_nifi_data/       │
    │                   ▼
    ▼              管理员在内部页
 普通用户文件中心    下拉切换用户 → 浏览
 可查看自己的数据    → 拉取到公司 Ceph
                     → 中心训练
    │
    ▼
 直接中心训练
```

### 说明
- 公有化用户：数据从一开始就在公司 Ceph `/home/yhz/in-data/{username}/` 下，普通用户自己可查看，管理员也可查看，无需额外拉取
- 私有化用户：数据在工厂 Ceph `{ceph_endpoint}/` 下，管理员手动拉取后存到公司 Ceph `/home/yhz/in-data/{username}/`

    ├── output_csv/
    ├── output_json/

### 3.3 私有化部署——工厂 Ceph 视角

> **关键**：一个工厂对应一个用户，工厂自己的 Ceph 上只有该工厂的数据，不存在多用户。

## 五、后端 API 改动清单

### 5.1 新增辅助函数（main.py）

| 函数 | 用途 |
|------|------|
| `_get_user_info(username)` | 从数据库查询用户完整信息（deployment_mode, ceph_endpoint） |
| `_resolve_user_storage_root(username)` | 根据部署模式返回存储根路径，并自动创建 `nifi-data/` 和 `real_nifi_data/` 子目录 |

```python
def _resolve_user_storage_root(username: str) -> Path:
    """根据用户部署模式返回存储根路径。
    
    公有化: /home/yhz/in-data/{username}/
    私有化: {ceph_endpoint}/   （工厂 Ceph 上只有一个用户，不加 username 子目录）
    """
    session = SessionLocal()
    try:
        user = session.query(IotUser).filter(IotUser.username == username).first()
        if user and user.deployment_mode == "private" and user.ceph_endpoint:
            root = Path(user.ceph_endpoint)
        else:
            root = IN_DATA_BASE_DIR / username
        (root / "nifi-data").mkdir(parents=True, exist_ok=True)
        (root / "real_nifi_data").mkdir(parents=True, exist_ok=True)
        return root
    finally:
        session.close()
```

| `_persist_to_in_data` | 写到 `IN_DATA_BASE_DIR/{factory_id}/{job_id}` | 同上，按部署模式路由 |

### 5.4 改动：文件中心增加 real_nifi_data 展示（main.py）

> **现状**：网站文件中心已能显示 `nifi-data`（通过 `GET /api/v1/files` 列表 + `api_get_factory_tree` 树形浏览）。
> **需求**：在现有文件中心中，增加对 `real_nifi_data` 的展示，使每个用户的 `nifi-data` 和 `real_nifi_data` **同时并列显示为两个根节点**。

#### 5.4.1 改动点

| 改动位置 | 当前行为 | 改动后 |
|----------|----------|--------|
| `api_get_factory_tree` (line 1387) | 只返回 `IN_DATA_BASE_DIR` 树（对应 nifi-data） | 返回 `nifi-data` + `real_nifi_data` 两个根节点树 |
| 文件中心列表（`GET /api/v1/files`） | 已通过 `_export_output_root` 同时列出 nifi 和 local 模式文件 | **无需改动**（已覆盖） |
| 如需普通用户独立访问 | 普通用户无独立文件中心入口（现有接口都需 `_require_admin`） | 新增无需 admin 权限的 `/api/v1/user/files/tree`，从 JWT 获取用户名 |

#### 5.4.2 改动后 API 返回格式

```python
@app.get("/api/v1/internal/factory-tree")
def api_get_factory_tree(request: Request, username: Optional[str] = Query(default=None)):
    """管理员内部页：查看指定用户的 nifi-data 和 real_nifi_data 树"""
    _require_admin(request)
    user = _get_user_info(username) if username else None
    resolved_username = username if username else "default"
    trace_id = make_trace_id(request.headers.get("x-trace-id"))
    
    storage_root = _resolve_user_storage_root(resolved_username)
    roots = []
    for subdir in ["nifi-data", "real_nifi_data"]:
        tree = _build_filesystem_tree(storage_root / subdir, label=subdir, max_depth=6)
        if tree:
            roots.append(tree)
    
    return ok({"username": resolved_username, "roots": roots}, trace_id)
```

> **核心变更**：树形浏览从仅展示 `IN_DATA_BASE_DIR`（nifi-data）的单一树，改为展示 `nifi-data` 和 `real_nifi_data` 两个并列根节点的双树结构。

#### 5.4.3 如需普通用户独立文件中心（不通过内部管理页）

当前所有文件浏览接口（`/api/v1/internal/*`）均需 `_require_admin`。如需普通用户也能在独立页面浏览自己的两个目录，新增：

```python
@app.get("/api/v1/user/files/tree")
def api_user_files_tree(request: Request):
    """普通用户文件中心：从 JWT 获取用户名，返回自己的 nifi-data 和 real_nifi_data"""
    user = _get_current_user_from_request(request)
    username = user["username"]
    trace_id = make_trace_id(request.headers.get("x-trace-id"))
    
    storage_root = _resolve_user_storage_root(username)
    roots = []
    for subdir in ["nifi-data", "real_nifi_data"]:
        tree = _build_filesystem_tree(storage_root / subdir, label=subdir, max_depth=6)
        if tree:
            roots.append(tree)
    
    return ok({"username": username, "roots": roots}, trace_id)
```

## 七、项目影响范围分析（基于当前代码状态）

### 7.1 全局概述

当前项目以"单工厂 + 全局路径"模式运行，所有路径写死为全局常量。改为"多用户 + 公有化/私有化"后，核心变更是**将所有写死的全局路径改为按用户动态解析**。以下按功能模块逐一分析影响。

### 7.2 全局路径常量（18 个，全部受影响的根因）

当前 `main.py` 顶部定义了 18 个全局路径常量，全部硬编码为 `/home/yhz/` 下的固定路径，按部署模式改动后必须全部改为动态解析：

| 常量 | 当前值（示例） | 改动后（公有化） | 改动后（私有化） |
|------|---------------|-----------------|-----------------|
| `NIFI_BASE_DIR` | `/home/yhz/nifi-data` | `{IN_DATA_BASE_DIR}/{username}/nifi-data` | `{ceph_endpoint}/nifi-data` |
| `NIFI_REAL_BASE_DIR` | `/home/yhz/real_nifi_data` | `{IN_DATA_BASE_DIR}/{username}/real_nifi_data` | `{ceph_endpoint}/real_nifi_data` |
| `IN_DATA_BASE_DIR` | `/home/yhz/in_data` | 保留根目录，子目录加 `{username}/` | 保留根目录（拉取后存放） |
| `NIFI_OUTPUT_DIR` | `/home/yhz/nifi-data/output_csv` | 动态，同上逻辑 | 动态，同上逻辑 |
| `NIFI_OUTPUT_JSON_DIR` | `/home/yhz/nifi-data/output_json` | 动态 | 动态 |

### 7.4 改动策略

**核心思路**：新增一个统一的 `_resolve_user_storage_root(username)` 函数，所有需要获取存储路径的地方都通过它获取，而非直接使用全局常量。

```
改动前（全局常量）:
  NIFI_BASE_DIR = /home/yhz/nifi-data           → 所有用户共享
  NIFI_REAL_BASE_DIR = /home/yhz/real_nifi_data  → 所有用户共享
  IN_DATA_BASE_DIR = /home/yhz/in_data           → 所有用户共享

改动后（动态解析）:
  _resolve_user_storage_root("zhangsan") → /home/yhz/in-data/zhangsan/         (公有化)
  _resolve_user_storage_root("wangwu")  → /mnt/factory-ceph-wangwu/            (私有化)
    其下包含:
      nifi-data/          ← 替代 NIFI_BASE_DIR
      real_nifi_data/     ← 替代 NIFI_REAL_BASE_DIR
```

## 九、关键设计决策

| 决策点 | 结论 |
|--------|------|
| 用户标识 | 使用 `username` 作为工厂标识，不再使用 `factory-001` 等抽象命名 |
| 每个用户目录结构 | 统一包含 `nifi-data/`（Local 产物）和 `real_nifi_data/`（NiFi 产物）两个子目录 |
| 公有化存储路径 | `/home/yhz/in-data/{username}/`，多用户并列存放 |
| 私有化存储路径 | `{ceph_endpoint}/`，直接包含 `nifi-data/` 和 `real_nifi_data/`（一个工厂 Ceph 只有一个用户，无需 `${username}` 子目录） |
| 私有化 Ceph 访问方式 | 通过文件系统挂载路径直接访问（CephFS），无需额外网络协议 |
| 管理员拉取方式 | 手动触发（内部管理页点击按钮），后续可扩展为定时自动拉取 |
| 拉取后数据位置 | `/home/yhz/in-data/{username}/`，与公有化用户并列存放 |
| 前端用户切换 | 内部管理页顶部下拉菜单覆盖所有用户（公有化+私有化），选择后动态刷新文件列表 |
| 普通用户文件中心 | 新增独立页面，所有登录用户可见，无需管理员权限 |
| 权限控制 | `/api/v1/internal/*` 需 `_require_admin`；`/api/v1/user/*` 只需普通登录 |

## 十、风险与应对

| 风险 | 应对 |
|------|------|
| 私有化用户 Ceph 未挂载或不可达 | 拉取前检查路径是否存在，返回明确错误信息 |
| 用户名与历史 factory-001 不兼容 | 实施时逐步迁移，旧数据保留在 `factory-001` 目录，新数据写入 `username` 目录 |
| 大文件拉取超时 | 拉取接口改为异步任务，返回任务 ID 供前端轮询进度 |
| 并发拉取导致磁盘 IO 过高 | 限制同时拉取任务数量，加入队列机制 |
| 下拉菜单用户过多 | 支持搜索/过滤，按用户名首字母分组 |
| `export_worker.py`/`silent_export_worker.py` 改动影响面大 | 先新建 `_resolve_user_storage_root` 统一入口，再逐文件迁移，保留旧逻辑作为 fallback |
| 工厂 Ceph 网络不通 | 需工厂 IT 配合开放端口或搭建 VPN；如无法连通，考虑工厂主动推送数据的反向方案 |
| 多用户同时操作同一 Ceph 目录 | 私有化部署下工厂侧写入、公司侧只读，冲突概率低；必要时加文件锁 |
| NiFi 容器多实例资源消耗 | 限制同时运行容器数，闲置容器自动停止，公有化用户共享一个 NiFi |

## 十一、多用户并发登录机制

### 11.1 当前认证架构

项目已具备多用户并发登录的基础能力，使用 **JWT + HttpOnly Cookie** 方案：

```
┌─────────────────────────────────────────────────────┐
│  浏览器 A (zhangsan)       浏览器 B (lisi)           │
│  ┌─────────────────┐      ┌─────────────────┐       │
│  │ Cookie:          │      │ Cookie:          │       │
│  │ access_token=    │      │ access_token=    │       │
│  │  eyJ...zhangsan  │      │  eyJ...lisi      │       │
│  └─────────────────┘      └─────────────────┘       │
│         │                        │                   │
│         ▼                        ▼                   │
│  ┌──────────────────────────────────────────────┐    │
│  │              FastAPI 后端                     │    │
│  │  _get_current_user_from_token(cookie)        │    │
│  │    → {username: "zhangsan", ...}             │    │
│  │    → {username: "lisi", ...}                 │    │
│  │                                              │    │
│  │  每个请求独立解析 Cookie → 确定当前用户身份   │    │
│  └──────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────┘
```

### 11.2 关键机制

| 机制 | 当前实现 | 多用户支持情况 |
|------|----------|---------------|
| 认证方式 | JWT token 存储在 HttpOnly Cookie | 不同浏览器/设备自动隔离，同浏览器不同用户需登出再登入 |
| 用户身份获取 | `_get_current_user_from_token(cookie)` 从 cookie 解析 JWT | 每次请求独立解析，天然支持多用户并发 |
| Token 有效期 | 15 分钟（`ACCESS_EXPIRE_SECONDS=900`） | 过期后自动跳转登录页 |
| 管理员校验 | `_require_admin(request)` 检查 JWT 中的 `is_admin` 字段 | 普通用户访问内部接口返回 401 |
| 登出机制 | 清除 cookie（`delete_cookie`） | 清除后浏览器视为未登录 |

### 11.3 当前缺口：用户数据隔离

虽然认证架构支持多用户并发登录，但**当前所有用户共享同一套全局路径**，这是本方案要解决的核心问题：

```
现状（问题）:
  zhangsan 登录 → 上传文件 → /home/yhz/nifi-data/inbox_csv/（全局）
  lisi 登录     → 上传文件 → /home/yhz/nifi-data/inbox_csv/（同一目录！）
  结果：所有用户文件混在一起，无法区分

方案目标:
  zhangsan 登录 → 上传文件 → /home/yhz/in-data/zhangsan/nifi-data/inbox_csv/
  lisi 登录     → 上传文件 → /home/yhz/in-data/lisi/nifi-data/inbox_csv/
  结果：用户数据完全隔离
```

### 11.4 改动后请求流程

每个请求需要在处理路径相关操作时，注入当前用户身份：

```python
# 当前模式（所有用户共享）
def upload_inbox_csv(request: Request, file: UploadFile):
    _require_admin(request)  # 只校验是否管理员
    dest = INBOX_CSV_DIR / file.filename  # 全局路径

# 改动后（按用户隔离）
def upload_inbox_csv(request: Request, file: UploadFile):
    _require_admin(request)
    user = _get_current_user_from_request(request)  # 从 JWT 获取用户名
    storage_root = _resolve_user_storage_root(user["username"])
    dest = storage_root / "nifi-data" / "inbox_csv" / file.filename
```

## 十二、拉取数据详细实现方案

### 12.1 拉取场景

管理员在内部管理页选中私有化用户后，将其工厂 Ceph 上的数据复制到公司 Ceph，用于模型训练：

```
拉取前:
  工厂 Ceph（私有化）              公司 Ceph
  /mnt/factory-ceph-wangwu/       /home/yhz/in-data/wangwu/
  ├── nifi-data/                  （空或旧数据）
  │   ├── output_csv/
  │   └── ...
  └── real_nifi_data/
      └── ...

拉取后:
  工厂 Ceph（私有化）              公司 Ceph
  /mnt/factory-ceph-wangwu/       /home/yhz/in-data/wangwu/
  ├── nifi-data/                  ├── nifi-data/          ← 复制
  │   ├── output_csv/             │   ├── output_csv/
  │   └── ...                     │   └── ...
  └── real_nifi_data/             └── real_nifi_data/     ← 复制
      └── ...                         └── ...
```

### 12.2 拉取 API 设计

**端点：** `POST /api/v1/internal/private-users/{username}/pull`

**请求体：**
```json
{
  "source_paths": [
    "/mnt/factory-ceph-wangwu/nifi-data/output_csv/sensor_2026-06.csv",
    "/mnt/factory-ceph-wangwu/real_nifi_data/export_jobs/job_001/"
  ],
  "target_subdir": "pulled_2026-06-02"
}
```

**参数说明：**

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `source_paths` | `list[str]` | 否 | 指定要拉取的文件/目录列表，为空则拉取全部 |
| `target_subdir` | `str` | 否 | 拉取后在公司侧的存放子目录，默认 `"pulled_{date}"` |

**返回：**
```json
{
  "success": true,
  "data": {
    "task_id": "pull_wangwu_20260602_001",
    "username": "wangwu",
    "status": "started",
    "total_files": 156,
    "total_bytes": 2147483648,
    "target_dir": "/home/yhz/in-data/wangwu/pulled_2026-06-02/"
  }
}
```

### 12.3 拉取实现方式

#### 方式一：同步拉取（小数据量，推荐先实现）

```python
@app.post("/api/v1/internal/private-users/{username}/pull")
def api_pull_private_user_data(username: str, request: Request, body: dict = Body(...)):
    _require_admin(request)
    trace_id = make_trace_id(request.headers.get("x-trace-id"))
    
    # 1. 获取用户信息
    user = _get_user_info(username)
    if not user or user.deployment_mode != "private":
        raise HTTPException(400, "该用户不是私有化部署用户")
    
    # 2. 检查 Ceph 是否可访问
    ceph_root = Path(user.ceph_endpoint)
    if not ceph_root.exists():
        raise HTTPException(503, f"工厂 Ceph 不可达: {ceph_root}")
    
    # 3. 确定拉取范围
    source_paths = body.get("source_paths") or []
    target_subdir = body.get("target_subdir") or f"pulled_{datetime.now().strftime('%Y-%m-%d')}"
    
    if not source_paths:
        source_paths = [str(ceph_root / "nifi-data"), str(ceph_root / "real_nifi_data")]
    
    # 4. 执行复制
    target_base = IN_DATA_BASE_DIR / username / target_subdir
    stats = {"files": 0, "bytes": 0}
    
    for src in source_paths:
        src_path = Path(src)
        if not src_path.exists():
            continue
        rel = src_path.relative_to(ceph_root) if ceph_root in src_path.parents or ceph_root == src_path else src_path.name
        dst = target_base / rel
        stats = _copy_with_stats(src_path, dst, stats)
    
    return ok({
        "username": username,
        "target_dir": str(target_base),
        "total_files": stats["files"],
        "total_bytes": stats["bytes"],
    }, trace_id)
```

#### 方式二：异步拉取（大数据量，后续扩展）

对于 GB 级别数据，同步 `shutil.copytree` 会阻塞请求。改为异步任务模式：

```
POST /pull → 创建任务，返回 task_id
GET /pull/{task_id}/status → 查询进度
GET /pull/{task_id}/cancel → 取消任务
```

实现可采用 `multiprocessing` 或 Celery 后台执行 `rsync` 命令。

### 12.4 增量拉取策略

| 场景 | 策略 |
|------|------|
| 首次拉取 | 全量复制 `nifi-data/` + `real_nifi_data/` |
| 后续拉取 | 对比文件修改时间（`mtime`），仅复制新文件/修改过的文件 |
| 冲突处理 | 同名文件以工厂侧（源）为准，覆盖公司侧 |

### 12.5 拉取安全性

| 风险 | 措施 |
|------|------|
| 路径穿越攻击 | `source_paths` 必须位于 `ceph_endpoint` 目录下，做 `_safe_relative_to` 校验 |
| 磁盘空间不足 | 拉取前检查目标磁盘剩余空间，不足时拒绝并提示 |
| 拉取过程中 Ceph 断连 | 使用 `try/except` 捕获 IOError，已复制的文件不回滚，返回部分成功状态 |

### 14.2 独立部署 vs SaaS 部署对比

| 维度 | 独立部署（卖产品） | SaaS 集中部署 |
|------|-------------------|---------------|
| **数据位置** | 客户自己的服务器/工厂内 | 公司云服务器 |
| **客户机器要求** | 需要一台 Linux 服务器（4核8G+） | 无需 |
| **网络要求** | 仅客户内网可用 | 公网 HTTPS |
| **运维方** | 客户自己 / 我方远程支持 | 我方 |
| **升级方式** | 客户拉取新版本镜像 / 安装包 | 我方直接更新云服务器 |
| **二次开发** | 客户可改源码 | 客户无法改 |
| **计费模式** | 一次性买断 + 年费维护 | 按月/年订阅 |
| **数据合规** | 最优（数据不出厂） | 受跨境数据合规约束 |
| **回款节奏** | 一次性大额 + 维护费 | 持续现金流 |
| **定制空间** | 客户可深度定制 | 标准化 |

### 14.5 数据库改造（重要！）

当前项目用 **SQLite**，多用户并发时性能不够。独立部署场景建议改用 **PostgreSQL**：

| 项 | SQLite（现状） | PostgreSQL（推荐） |
|----|---------------|-------------------|
| 并发性能 | 单写多读，差 | 高并发读写，优秀 |
| 文件大小 | 适合 < 100GB | TB 级 |
| 部署 | 零配置 | 需要容器 |
| 备份 | 拷贝 .db 文件 | `pg_dump` / 容器卷 |
| 适合场景 | 单用户/开发 | **多用户生产** |

**改造点：**
- `db_models.py` 已经用 SQLAlchemy，只需把 `engine` 改为 PostgreSQL
- 增加 `IOT_DATABASE_URL=postgresql://iot:xxx@postgres/iot` 环境变量

### 14.6 多租户/多工厂（独立部署版）

独立部署给客户后，**客户本身就是多工厂**（一个客户可能有多个工厂）：

```
客户：XX 集团
├── 工厂 A（北京）
├── 工厂 B（上海）
├── 工厂 C（广州）
└── 工厂 D（深圳）

→ 在我们的系统里注册为 4 个用户（A/B/C/D）
→ 数据分别存到 /in-data/A/、/in-data/B/、/in-data/C/、/in-data/D/
→ 客户的 IT 管理员用 admin 账号统一管理
```

**对接到公有/私有化的判断：**

| 客户场景 | 部署模式 | 说明 |
|----------|---------|------|
| 客户没自己的 Ceph | 公有化 | 数据存到独立部署服务器的本地磁盘 |
| 客户有 Ceph，希望数据在自己 Ceph | 私有化 | `ceph_endpoint` 指向客户 Ceph |

**两种模式可同时存在**：客户主厂用公有化（数据存部署服务器），分厂用私有化（数据存分厂 Ceph）。

### 14.7 独立部署的工程化要求

### 14.8 三种部署模式的关系

## 十五、跨网络多用户部署方案（不同局域网、不同设备）

> **核心问题**：每个工厂（用户）使用的是不同的机器，位于不同的局域网（甚至不同城市、不同网络运营商），不在同一个局域网内。如何让多用户都能访问同一套网站后端？

### 14.1 当前部署现状

```
当前项目部署（本地单点模式）:
  ┌─────────────────────────────────────────────┐
  │  公司服务器：home/yhz/iot/                   │
  │  ├── v1-backend/     (FastAPI 端口 8081)     │
  │  ├── v1-frontend/    (Vite 端口 5173)        │
  │  ├── docker/         (NiFi、MySQL)           │
  │  └── /home/yhz/nifi-data/  (数据)            │
  └─────────────────────────────────────────────┘
  ↑ 单机运行，仅本机或同局域网可访问
```

**当前局限：**
- 后端监听 `127.0.0.1:8081`，仅本机可访问
- 前端监听 `127.0.0.1:5173`，仅本机可访问
- 没有公网 IP/域名
- 没有反向代理
- 没有 HTTPS 证书

**工厂环境：**
- 各工厂位于不同城市、不同 ISP
- 多数工厂仅有内网 IP，无公网 IP
- 工厂设备（PC、笔记本、扫码枪）需要能访问网站

### 14.2 三种可行的多用户部署架构

#### 方案 A：集中式 SaaS 部署（推荐⭐⭐⭐⭐⭐）

> **思路**：所有用户统一访问部署在云服务器或公司机房的中央网站。私有化用户的工厂 Ceph 通过公网或 VPN 与中央服务器拉取数据。

```
                  公网（HTTPS）
                       │
       ┌───────────────┼───────────────┐
       │               │               │
       ▼               ▼               ▼
  ┌─────────┐     ┌─────────┐     ┌─────────┐
  │ 工厂 A   │     │ 工厂 B   │     │ 工厂 C   │
  │ 浏览器   │     │ 浏览器   │     │ 浏览器   │
  │ (zhangsan)│    │ (lisi)  │     │ (wangwu) │
  └────┬─────┘    └────┬─────┘    └────┬─────┘
       │               │               │
       │     HTTPS over Internet       │
       └───────────────┬───────────────┘
                       ▼
        ┌────────────────────────────┐
        │  云服务器 / 公司机房         │
        │  ┌──────────────────────┐  │
        │  │ Nginx + HTTPS 证书    │  │
        │  └──────────┬───────────┘  │
        │  ┌──────────▼───────────┐  │
        │  │ FastAPI 后端          │  │
        │  │ (监听 0.0.0.0:8081)  │  │
        │  └──────────┬───────────┘  │
        │  ┌──────────▼───────────┐  │
        │  │ Vite 前端构建产物     │  │
        │  │ (Nginx 静态托管)      │  │
        │  └──────────────────────┘  │
        │  ┌──────────────────────┐  │
        │  │ 公司 Ceph / S3 存储   │  │
        │  │ /in-data/{username}/ │  │
        │  └──────────────────────┘  │
        └────────────────────────────┘
                       ▲
                       │  定时拉取 / 反向代理
       ┌───────────────┼───────────────────┐
       │               │                   │
  ┌────▼─────┐    ┌────▼─────┐        ┌────▼─────┐
  │ 工厂 A    │    │ 工厂 B    │        │ 工厂 C    │
  │ Ceph     │    │ Ceph     │        │ Ceph     │
  │ (私有)   │    │ (私有)   │        │ (私有)   │
  └──────────┘    └──────────┘        └──────────┘
```

**优点：**
- 工厂无需任何部署，浏览器访问 URL 即可
- 集中运维，升级只需更新中央服务器
- 公有化/私有化统一接口
- 可走 CDN 加速前端静态资源

**缺点：**
- 需要云服务器（成本）
- 需要公网 IP / 域名 / HTTPS 证书
- 私有化用户的数据需从工厂 Ceph 拉到公司（已有方案）

**成本估算：**

| 资源 | 规格 | 月成本（参考） |
|------|------|---------------|
| 云服务器（4核8G） | 阿里云 ECS / 华为云 | ¥200-500 |
| 带宽（5Mbps） | 公网出方向 | ¥100-300 |
| 域名 | .com / .cn | ¥60/年 |
| HTTPS 证书 | Let's Encrypt（免费） | ¥0 |
| 公司 Ceph 存储 | 1-10TB | ¥100-500 |
| **合计** | | **约 ¥500-1500/月** |

#### 方案 B：每工厂独立部署（不推荐⭐⭐）

> **思路**：在每个工厂的机器上独立部署一套完整网站，工厂之间互不连通。

```
   工厂 A 内网             工厂 B 内网             工厂 C 内网
  ┌──────────┐           ┌──────────┐           ┌──────────┐
  │ FastAPI  │           │ FastAPI  │           │ FastAPI  │
  │ Vite     │           │ Vite     │           │ Vite     │
  │ SQLite   │           │ SQLite   │           │ SQLite   │
  │ Ceph     │           │ Ceph     │           │ Ceph     │
  └──────────┘           └──────────┘           └──────────┘
   仅本工厂访问            仅本工厂访问            仅本工厂访问
```

**优点：** 数据不出厂，最高的数据隔离
**缺点：**
- N 个工厂 = N 套部署
- 升级困难（需逐个工厂推送）
- 跨工厂训练数据汇总困难
- 公司无法集中管理
- **不适合本方案**（项目需要公司侧统一管理 + 训练）

#### 方案 C：混合部署（折中⭐⭐⭐）

> **思路**：公有化用户走云服务器集中访问，私有化用户在自己的工厂内网部署。

```
  公有化用户 → 云服务器（中央网站）
  私有化用户 → 工厂内网（独立部署）
                 ↓
              工厂数据回传公司（拉取）
```

**缺点：** 部署两套，运维复杂度高。

### 14.3 推荐方案 A 详细实施

#### 14.3.1 域名与 HTTPS

| 域名 | 购买 `iot.example.com` 或使用子域 `iot.company.com` | 一年 ¥60-100 |
| HTTPS 证书 | Let's Encrypt（免费，自动续期） | 用 `certbot` 申请 |
| DNS 解析 | A 记录指向云服务器公网 IP | 腾讯云 DNSPod / 阿里云 DNS |

#### 14.3.2 Nginx 反向代理配置

```nginx
# /etc/nginx/conf.d/iot.conf
server {
    listen 80;
    server_name iot.example.com;
    return 301 https://$server_name$request_uri;  # 强制 HTTPS
}

server {
    listen 443 ssl http2;
    server_name iot.example.com;
    
    # SSL 证书（Let's Encrypt）
    ssl_certificate     /etc/letsencrypt/live/iot.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/iot.example.com/privkey.pem;
    
    # 前端静态资源
    location / {
        root /home/yhz/iot/v1-frontend/dist;  # Vite 构建产物
        try_files $uri $uri/ /index.html;
    }
    
    # 后端 API 反向代理
    location /api/ {
        proxy_pass http://127.0.0.1:8081;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        
        # 大文件上传支持
        client_max_body_size 500M;
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }
    
    # 文件下载
    location /files/ {
        proxy_pass http://127.0.0.1:8081;
        proxy_set_header X-Accel-Redirect $upstream_http_x_accel_redirect;
    }
}
```

#### 14.3.5 防火墙与安全组

| 端口 | 用途 | 是否开放 |
|------|------|----------|
| 80 | HTTP（重定向到 HTTPS） | ✅ |
| 443 | HTTPS | ✅ |
| 22 | SSH 运维 | ⚠️ 仅限运维 IP 白名单 |

### 14.4 私有化用户的 Ceph 拉取通道

私有化用户的工厂 Ceph 不在公网，公司服务器如何拉取数据？有三种方式：

#### 方式 1：工厂侧公网暴露 CephFS（不推荐）

```
工厂：开放 CephFS 端口（6789、3300）→ 公司直接挂载
风险：暴露在公网，安全风险高
```

#### 方式 2：反向 SSH 隧道（推荐⭐⭐⭐⭐）

> 项目已有 `scripts/ssh_tunnel.sh` 工具，可直接使用。

```
公司服务器（公网）          工厂内网
┌──────────────┐         ┌──────────────┐
│ 监听拉取任务  │         │              │
│              │ ◄────── │ 主动建立隧道  │
│              │  HTTPS  │              │
└──────────────┘         └──────────────┘
```

**实施步骤：**

1. 工厂侧执行反向 SSH 隧道，保持长连接
   ```bash
   # 在工厂机器执行
   ssh -fN -R 0.0.0.0:22001:127.0.0.1:6789 root@iot.example.com
   # 公司侧 22001 端口映射到工厂侧 6789 端口
   ```

2. 公司服务器配置 `ceph_endpoint`：
   ```
   ceph_endpoint = ssh://localhost:22001/mnt/cephfs
   # 或
   ceph_endpoint = /mnt/factory-ceph-wangwu/  # 通过 sshfs 挂载
   ```

3. 拉取数据时，正常访问 `/mnt/factory-ceph-wangwu/`

**优点：**
- 工厂防火墙无需开放任何端口
- 公司公网 IP 固定，便于工厂 IT 添加白名单
- SSH 隧道本身加密

**缺点：**
- 工厂侧需保持一台机器在线
- 隧道断开需要重连（建议用 `autossh` 自动重连）

#### 方式 3：工厂主动推送（推荐⭐⭐⭐⭐⭐）

> 工厂侧定时/主动把数据推到公司 S3/OSS，公司侧从 S3 拉取。

```
工厂侧定时任务                公司 S3 桶
┌────────────┐               ┌─────────────┐
│ cron 每小时│ ──── push ──→ │ s3://iot/   │
│ rsync/s3cmd│               │  wangwu/    │
└────────────┘               └──────┬──────┘
                                     │ 拉取
                                     ▼
                            ┌──────────────┐
                            │ 公司 Ceph    │
                            │ /in-data/    │
                            │  wangwu/     │
                            └──────────────┘
```

**优点：**
- 工厂侧完全控制何时推送
- 公司侧无需任何入站连接
- 走 S3 协议，传输可靠
- 可走 CDN 加速

**缺点：**
- 需要工厂侧部署推送脚本
- 数据有 1 小时延迟

## 十五、实际部署难点分析

### 15.1 CephFS 挂载与运维

| 难点 | 说明 | 应对 |
|------|------|------|
| **CephFS 挂载稳定性** | 工厂 Ceph 与公司服务器之间的网络抖动可能导致 CephFS 挂载断开 | 使用 `autofs` 自动挂载/卸载；定期心跳检测挂载状态；挂载失败时 API 返回明确错误而非 500 |
| **多工厂 Ceph 管理** | 每个私有化工厂一台 Ceph，如果有 N 个工厂就需要 N 个挂载点 | 统一挂载到 `/mnt/factory-ceph-{username}/`，在用户注册时创建挂载点；建议使用 Ansible 自动化挂载管理 |
| **Ceph 权限** | 工厂 Ceph 可能只允许特定 IP 访问，或需要密钥认证 | 在 `ceph_endpoint` 字段中支持完整的挂载信息（IP、密钥路径、挂载选项） |
| **读/写并发** | 工厂和公司同时操作同一 Ceph 目录 | 私有化部署下，工厂侧写入，公司侧只读拉取，冲突概率低；必要时加文件锁 |

### 13.2 NiFi 容器多实例管理

| 难点 | 说明 | 应对 |
|------|------|------|
| **每用户独立 NiFi 实例** | 私有化用户的 NiFi 需要挂载工厂 Ceph，不能与公有化用户共享同一 NiFi 容器 | 当前 `nifi_orchestrator.py` 启动单容器，需改为按用户启动/管理容器 |
| **容器资源消耗** | 每个 NiFi 容器消耗 2-4GB 内存，N 个用户 = N × 3GB | 限制同时运行的 NiFi 容器数量；闲置容器自动停止；公有化用户可共享一个 NiFi |
| **端口冲突** | 每个 NiFi 容器需要独立端口 | 使用 Docker 动态端口映射（`-p 0:8443`），端口号记录在数据库中 |
| **容器生命周期** | 私有化用户的 NiFi 容器何时启动/停止 | 按需启动（用户触发导出任务时启动），闲置 30 分钟后自动停止 |

### 13.3 数据迁移与兼容性

| 难点 | 说明 | 应对 |
|------|------|------|
| **`factory-001` 历史数据** | 当前所有数据以 `factory-001` 为标识，`ExportJobModel` 表、文件注册表、磁盘文件都使用此 ID | 分两步迁移：1) 新建 `username` 字段，保留 `factory_id` 做 fallback；2) 将 `factory-001` 数据迁移到对应用户目录 |
| **数据库迁移** | `ALTER TABLE iot_users ADD COLUMN` 需要处理已有数据 | 默认已有用户 `deployment_mode="public"`，`ceph_endpoint=""` |
| **前端兼容** | 前端代码中可能硬编码了 `factory-001` | 全局搜索替换，改为从 API 获取当前用户信息 |

### 15.4 网络与传输

| 难点 | 说明 | 应对 |
|------|------|------|
| **工厂 ↔ 公司网络连通性** | 私有化工厂的 Ceph 可能部署在内网，公司服务器无法直接访问 | 需要工厂侧开放 CephFS 端口（6789）或搭建 VPN 隧道 |
| **大文件拉取速度** | 从一个工厂拉取 10GB 数据，在 100Mbps 带宽下需要约 15 分钟 | 拉取改为异步任务；支持断点续传；支持增量拉取（只拉新文件） |
| **防火墙/NAT** | 工厂网络通常有严格的防火墙规则 | 需要工厂 IT 配合开放端口；或使用反向代理（工厂主动推送数据到公司） |

### 13.5 用户管理与配置

| 难点 | 说明 | 应对 |
|------|------|------|
| **注册时无法确定部署模式** | 用户自己注册时不知道自己是公有化还是私有化 | 注册默认 `public`，管理员后续在用户管理页修改 |
| **Ceph 路径配置** | 管理员需要知道每个私有化工厂的 Ceph 挂载路径 | 在用户管理页提供"配置 Ceph 路径"表单，由管理员填写 |
| **多管理员并发操作** | 两个管理员同时拉取不同用户数据，可能产生 IO 争抢 | 加入拉取任务队列，限制同时拉取数 |

### 15.6 环境变量与配置管理

| 难点 | 说明 | 应对 |
|------|------|------|
| **当前配置方式** | 大量路径和配置通过代码顶部全局变量或环境变量设置，不适用于多用户 | 全局变量改为函数动态解析；环境变量仅保留真正全局的配置（如 SECRET_KEY） |
| **`.env` 文件** | 当前 `.env` 包含 `NIFI_BASE_DIR` 等路径 | 删除或标记为 deprecated，不再从环境变量读取路径 |

### 15.7 日志与监控

| 难点 | 说明 | 应对 |
|------|------|------|
| **日志中需要区分用户** | 当前日志使用 `trace_id`，但无法区分是哪个用户的操作 | 在 `trace_id` 或日志中增加 `username` 字段 |
| **拉取任务监控** | 管理员需要知道拉取进度、成功/失败状态 | 拉取任务记录到数据库，提供查询接口 |
| **Ceph 挂载健康监控** | 需要监控各工厂 Ceph 挂载是否正常 | 定时健康检查（`os.path.exists`），异常时告警 |

## 十六、验收标准

1. 公有化用户注册后，数据导出产物出现在 `/home/yhz/in-data/{username}/nifi-data/` 下
2. 私有化用户注册后，数据导出产物出现在工厂 Ceph `{ceph_endpoint}/nifi-data/` 下
3. 管理员登录内部管理页，顶部下拉菜单列出所有用户（公有化+私有化），每项标注部署模式
4. 管理员切换用户后，文件区域正确显示该用户的 `nifi-data` 和 `real_nifi_data`
5. 管理员选中私有化用户时显示"拉取到公司"按钮，可拉取数据；选中公有化用户时该按钮隐藏
6. 普通用户登录后，在"文件中心"页面可看到自己的 `nifi-data` 和 `real_nifi_data`
7. 普通用户看不到内部管理页
8. 非管理员用户无法访问任何 `/api/v1/internal/*` 接口
