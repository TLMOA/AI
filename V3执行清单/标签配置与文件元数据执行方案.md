# V3 执行清单：标签配置与文件元数据方案

## 1. 目标

为每个文件引入独立配置文件，统一记录文件来源、是否含标签、标签列、标签名字、可用标签范围、处理方式和存放目录，确保数据库导出、文件上传、预览编辑、手动打标、自动打标都能基于同一套元数据运行。

## 2. 需求范围

### 2.1 必须支持的场景

1. 数据库导出时，用户必须填写：
   - 是否含标签
   - 若含标签：标签列
   - 标签名字
   - 若不含标签：候选标签范围
2. 文件上传时，用户必须填写：
   - 是否含标签
   - 若含标签：标签列
   - 标签名字
   - 若不含标签：候选标签范围
3. 对已有文件进行手动打标签或自动打标签后，网站必须回写配置文件，记录：
   - 标签列
   - 标签名字
   - 结果文件目录
   - 处理方式
4. 无标签文件正常放入普通目录，有标签文件放入标签目录。
5. 文件预览编辑区新增字段最多只允许新增 1 列，且列名固定为 tag。
6. 自动打标签支持按多列组合规则配置“根据哪些列打什么标签”。

### 2.2 约束

1. 每个数据文件的元数据以加密形式存储在该文件的 xattr 扩展属性中，数据与元数据一一对应。
2. 元数据中凡是出现"标签列"的地方，都必须同步写入"标签名字"。
3. 无标签文件的元数据必须写入候选标签范围，后续手动标签只能从该范围中选择。
4. 有标签文件的元数据必须写入标签列、标签名字，并保留来源信息。

## 3. 元数据存储方案：xattr + 加密

### 设计理念

**磁盘上不存在任何独立的配置文件**。元数据通过加密后写入数据文件的 Linux 扩展属性（xattr），一个数据文件在磁盘上就是它自己，没有配对的 `.meta.json`。

```
传统方案：
  sensor_data.csv              ← 数据文件
  sensor_data.csv.meta.json    ← 配置文件（任何人都能看到）

本方案：
  sensor_data.csv
  │
  │  文件内容（cat 看到）：正常的 CSV 数据，一行不多
  │
  │  inode 扩展属性（cat/ls 均不可见）：
  │  ┌──────────────────────────────────────┐
  │  │ user.meta     = 加密密文               │
  │  │ user.checksum = SHA-256 校验码（明文）   │
  │  └──────────────────────────────────────┘
  │
  └── 文件删除时 xattr 自动释放，无需额外清理
```

**关键特性**：

| 特性 | 说明 |
|------|------|
| 零额外文件 | 每个数据文件不再需要配对的 `.meta.json` |
| inode 级附着 | 元数据属于文件系统元信息，不属于文件内容 |
| 文件操作自动跟随 | 改名、移动无需更新任何配对，xattr 依附 inode |
| 加密不可见 | 即使 root 用 `getfattr` 强行读取，也只能看到密文 |
| 零外部依赖 | Python 标准库 `os` + `hashlib` + `hmac` + `secrets` 全部实现 |

#### 字段说明（含来源标注）

> **自动**：系统写入，无需用户操作。**用户**：需用户在对应页面上填写/选择。

| 字段 | 类型 | 必须 | 来源 | 说明 |
|------|------|:--:|:--:|------|
| `fileId` | string | 是 | 自动 | 系统根据文件路径 + 时间戳生成唯一标识（如 `file_d29b73dd23`），用户不可见 |
| `fileName` | string | 是 | 自动 | 从数据文件的实际文件名读取，用户不可修改 |
| `sourceType` | string | 是 | 自动 | 系统根据触发入口自动写入：`db_export`（数据库导出）/ `upload`（文件上传）/ `manual_tag`（手动打标生成）/ `auto_tag`（自动打标生成） |
| `storageType` | string | 是 | 自动 | 系统根据 `hasTag` 和落盘目录自动写入：有标签文件 → `tagged`，无标签文件 → `plain` |
| `storagePath` | string | 是 | 自动 | 文件落盘时系统自动记录绝对路径，**仅后端内部使用**，永不出现在 API 响应中 |
| `hasTag` | boolean | 是 | **用户** | 导出/上传时用户选择：该文件中是否已经包含标签列 |
| `tagColumn` | string | 条件 | **用户** | `hasTag=true` 时必填，用户指定文件中哪一列是标签列（如 `"status"`、`"label"`） |
| `tagName` | string | 条件 | **用户** | `hasTag=true` 时必填，标签列的人类可读名称（如 `"故障级别"`、`"设备状态"`），用于页面展示 |
| `tagRange` | array | 条件 | **用户** | `hasTag=false` 时必填，用户指定候选标签范围（如 `["故障","预警","正常"]`），后续手动打标只能从此范围内选择 |
| `tagStrategy` | string | 否 | 自动 | 系统根据操作入口写入：导出/上传已有标签 → `column_tag`，手动打标 → `manual_range`，自动打标 → `auto_rule` |
| `tagRule` | object | 否 | **用户** | 仅在自动打标时由用户配置，定义参与打标的列、条件和输出标签（见 [3.1 示例](#31-建议字段)） |
| `trainable` | boolean | 否 | 自动 | 系统默认 `true`，表示该文件可用于模型训练。管理员可通过接口关闭 |
| `categoryId` | string | 否 | 自动+用户 | 系统根据文件来源目录自动归类，用户可在页面上修改（如 `"cat_001"`=设备日志，`"cat_002"`=传感器数据） |
| `categoryName` | string | 否 | 自动+用户 | 与 `categoryId` 对应的人类可读名称，系统根据目录预设，用户可改 |
| `description` | string | 否 | **用户** | 可选的文件描述文本，由用户在导出/上传/预览页面填写 |
| `columns` | array | 否 | 自动 | 系统读取文件第一行自动解析列名列表（如 `["device_id","temperature","timestamp"]`） |
| `rowCount` | number | 否 | 自动 | 系统统计文件数据行数（不含表头），写入时自动计数 |
| `fileSize` | number | 否 | 自动 | 系统通过 `os.path.getsize()` 自动获取（单位：字节） |
| `createdAt` | string | 是 | 自动 | 文件首次生成时系统写入 ISO 8601 时间戳 |
| `updatedAt` | string | 是 | 自动 | 每次 xattr 元数据内容变更时系统自动更新 ISO 8601 时间戳 |

### 3.2 规则

1. `hasTag = true` 时，必须存在 `tagColumn` 和 `tagName`。
2. `hasTag = false` 时，必须存在 `tagRange`。
3. 如果文件经过手动/自动打标生成新文件，必须对新文件写入 xattr 元数据并继承必要字段。
4. 如果是普通目录文件，但后续被打标进入标签目录，则元数据中的 `storageType` 需要同步更新。

### 3.3 加密实现

#### 3.3.1 算法设计

采用 **AES-256-GCM 认证加密**，基于 `cryptography` 库实现，业界标准。

**加密流程**：

```
输入: meta dict
    │
    ├── json.dumps → plaintext
    │
    ├── os.urandom(12) → 12 字节 nonce（保证每次加密结果不同）
    │
    ├── AESGCM.encrypt(nonce, plaintext, None)
    │     ├── AES-256 加密 plaintext
    │     └── GHASH 计算 16 字节认证标签（防篡改）
    │     └── 输出: ciphertext（含 16 字节 GCM tag）
    │
    └── base64(nonce + ciphertext) → 写入 user.meta

注：GCM 模式的认证标签已内嵌于 ciphertext 尾部，由 cryptography 库自动管理，
    无需额外 HMAC。
```

**解密流程**：

```
输入: getxattr("user.meta")
    │
    ├── base64 解码 → nonce(12B) + ciphertext(含 16B GCM tag)
    │
    ├── AESGCM.decrypt(nonce, ciphertext, None)
    │     ├── AES-256 解密
    │     └── 自动验证 GCM 认证标签 → 不匹配则直接抛异常
    │     └── 输出: plaintext
    │
    ├── SHA-256(plaintext) 对比 user.checksum → 二次完整性校验（防御磁盘静默损坏）
    │
    └── json.loads → meta dict
```

**密钥**：32 字节随机密钥，base64 编码后写入 systemd 环境变量 `META_XATTR_KEY`，不落盘。进程启动时读取一次。

| 参数 | 长度 | 作用 |
|------|:--:|------|
| META_KEY | 32B | AES-256 加密密钥 |
| nonce | 12B | 保证同一明文每次加密结果不同 |
| GCM tag | 16B | 认证标签（防篡改，密文尾部自动携带） |
| checksum | 64B(hex) | SHA-256 完整性校验（防御磁盘静默损坏） |

#### 3.3.2 核心代码

```python
import os
import json
import hashlib
import hmac
import base64
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

META_KEY = base64.b64decode(os.environ["META_XATTR_KEY"])
aesgcm = AESGCM(META_KEY)
XATTR_META = "user.meta"
XATTR_CHECKSUM = "user.checksum"


def write_meta(file_path: str, meta: dict) -> None:
    """AES-256-GCM 加密写入元数据到文件 xattr。

    GCM 模式自带认证标签，无需额外 HMAC。
    不创建任何额外文件，磁盘上只有数据文件本身。
    """
    plaintext = json.dumps(meta, ensure_ascii=False, separators=(",", ":")).encode()
    nonce = os.urandom(12)                     # GCM 推荐 12 字节 nonce
    ciphertext = aesgcm.encrypt(nonce, plaintext, None)  # 密文 + 16B GCM tag
    payload = base64.b64encode(nonce + ciphertext)
    os.setxattr(file_path, XATTR_META, payload)
    os.setxattr(file_path, XATTR_CHECKSUM,
                hashlib.sha256(plaintext).hexdigest().encode())


def read_meta(file_path: str) -> dict:
    """读取并解密文件 xattr 中的元数据。

    GCM 解密时自动验证认证标签，校验失败直接抛出异常。
    """
    payload = base64.b64decode(os.getxattr(file_path, XATTR_META))
    nonce = payload[:12]
    ciphertext = payload[12:]

    try:
        plaintext = aesgcm.decrypt(nonce, ciphertext, None)
    except Exception:
        raise ValueError("元数据 GCM 认证失败：文件可能被篡改")

    expected_hash = hashlib.sha256(plaintext).hexdigest()
    actual_hash = os.getxattr(file_path, XATTR_CHECKSUM).decode()
    if not hmac.compare_digest(expected_hash, actual_hash):
        raise ValueError("元数据 checksum 校验失败：数据损坏")

    return json.loads(plaintext)


def has_meta(file_path: str) -> bool:
    """检查文件是否已有 xattr 元数据。"""
    try:
        return XATTR_META in os.listxattr(file_path)
    except OSError:
        return False


def delete_meta(file_path: str) -> None:
    """删除文件的 xattr 元数据。"""
    for attr in (XATTR_META, XATTR_CHECKSUM):
        try:
            os.removexattr(file_path, attr)
        except OSError:
            pass
```

### 3.4 训练文件元数据方案

> **定位说明**：本模块不负责训练文件选取的前端界面，选取交互由大模型团队在另一个模块独立实现。这里仅提供标准化的存储结构和查询接口，供下游模块调用。

#### 3.4.1 设计原则

- **xattr 是唯一真相源**：每个数据文件的元数据以加密形式存储在该文件的 `user.meta` 扩展属性中，不额外创建独立的配置文件或训练清单文件。
- **路径隔离**：`storagePath` 仅在后端内部使用，API 响应中不包含此字段，下游模块通过 `fileId` 间接引用实际文件。
- **按需扩展**：元数据中与训练相关的字段（`trainable`、`categoryId`、`columns` 等）均为可选，不影响现有标签管理流程。

#### 3.4.5 安全隔离方案

核心要求：元数据不可被任何人直接访问，只能通过 API 间接获取摘要数据。

**四层隔离**：

```
任何人（包括 SSH 登录的开发运维人员）
    │
    ▼ ls /home/yhz/nifi-data/output_csv/
┌──────────────────────────────┐
│  磁盘上只有数据文件            │  → 没有 .meta.json 文件可看
│  sensor_data.csv             │
│  没有任何配置文件              │
└──────────────────────────────┘
    │
    ▼ cat sensor_data.csv
┌──────────────────────────────┐
│  文件内容正常                   │  → xattr 不属于文件内容，cat 看不到
│  device_id,temperature,...   │
└──────────────────────────────┘
    │
    ▼ getfattr -d sensor_data.csv  (即使知道秘密路径)
┌──────────────────────────────┐
│  user.meta="eUp4V09FS2..."   │  → 密文，无 META_XATTR_KEY 不可解密
│  user.checksum="abc123..."   │
└──────────────────────────────┘
    │
    ▼ 浏览器 / API 调用（唯一合法路径）
┌──────────────────────────────┐
│  Nginx + JWT 认证 + API      │  → 仅返回元数据摘要，不含 storagePath
│  响应中不含真实路径             │
└──────────────────────────────┘
```

**攻击面评估**：

| 攻击方式 | 结果 |
|----------|------|
| 浏览器 URL 访问 | ❌ Nginx 不暴露数据目录 |
| API 调用 | ❌ 响应不含 `storagePath` |
| SSH `ls` / `cat` | ❌ xattr 不显示，无独立配置文件 |
| SSH `getfattr` 读取 | ❌ 看到密文，无密钥不可解密 |
| 文件系统备份 | ❌ 默认 `tar`/`rsync` 不保留 xattr |
| 物理硬盘窃取 | ❌ 密文 + 密钥在环境变量中分离 |
| root 提权 + 读 systemd env | ⚠️ 可获取密钥（运维管控层防范） |

**xattr 操作注意事项**：

| 操作 | 正确方式 | 错误方式 |
|------|------|------|
| 复制文件 | `cp --preserve=xattr src dst` | `cp src dst`（xattr 丢失） |
| 同步 | `rsync -X src dst` | `rsync src dst`（xattr 丢失） |
| 打包 | `tar --xattrs -cf arch.tar files/` | `tar -cf arch.tar files/`（xattr 丢失） |
| Docker 卷 | 默认支持 | — |

#### 3.4.6 配置管理

**版本控制**：
- 修改 xattr 元数据前，先将当前内容导出到备份文件：直接导出解密后的 JSON，base64 后存入带时间戳的备份
- 保留最近 5 个备份版本，超出自动清理
- 变更记录写入审计日志

**更新机制**：
- 数据文件与 xattr 元数据由同一后端事务保证一致性（`write_meta()` 是原子操作）
- xattr 变更会触发文件 mtime 变化（取决于文件系统和操作），后端通过 mtime 对比自动刷新内存索引
- 下游模块调用 `/api/v1/training/files` 时获取的始终是最新数据

**备份策略**：

| 类型 | 频率 | 保留 | 内容 |
|------|------|------|------|
| 实时备份 | 每次修改前 | 5 个版本 | 单个文件 xattr 解密后 JSON 的备份 |
| 每日全量 | 每天 02:00 | 30 天 | 全量 `getfattr -d` 导出 + 加密 tar |
| 每周归档 | 每周日 03:00 | 90 天 | 全量打包 + 数据文件抽样 |

**从旧 `.meta.json` 迁移**（已有项目一次性执行）：

```python
from pathlib import Path
import json

def migrate_all(base_dir: str):
    """一次性将存量 .meta.json 迁移到 xattr。"""
    base = Path(base_dir)
    for meta_path in base.rglob("*.meta.json"):
        meta = json.loads(meta_path.read_text())
        data_file = Path(str(meta_path)[:-len(".meta.json")])
        if data_file.exists():
            write_meta(str(data_file), meta)
            meta_path.unlink()  # 删除旧的 .meta.json
            print(f"已迁移: {data_file.name}")
```

## 5. 后端改造清单

### 5.1 导出接口

1. 扩展导出请求参数，接收：
   - `hasTag`
   - `tagColumn`
   - `tagName`

2. 导出结果写入文件后，调用 `write_meta()` 将元数据加密写入该文件的 xattr 扩展属性。
3. 若 `hasTag = true`，必须校验 `tagColumn` 和 `tagName` 非空。
4. 若 `hasTag = false`，必须校验 `tagRange` 非空。

### 5.2 上传接口

1. 扩展上传请求参数，接收：
   - `hasTag`
   - `tagColumn`
   - `tagName`
   - `tagRange`
2. 写入普通目录或标签目录时，调用 `write_meta()` 将元数据写入文件 xattr。
3. 标签文件进入标签目录，普通文件进入普通目录。
4. 上传后文件的元数据必须可被 `has_meta()` + `read_meta()` 读取。

### 5.3 预览接口

1. 预览接口通过 `read_meta()` 读取文件 xattr 元数据。
2. 如果元数据声明了 `tagColumn`，预览输出要识别该列。
3. 如果文件无标签，但允许新增标签列，则新增列名只能是 `tag`。
4. 预览返回值里附带元数据摘要：
   - `hasTag`
   - `tagColumn`
   - `tagName`
   - `tagRange`

### 5.4 手动打标签接口

1. 校验标签值必须来自元数据中的候选标签范围。
2. 输出文件后通过 `write_meta()` 写入新文件的 xattr 元数据。
3. 元数据中必须记录最终标签列和标签名字。
4. 若新增了 `tag` 列，必须同步更新文件 xattr 元数据。

### 5.5 自动打标签接口

1. 扩展规则结构，支持多列条件。
2. 自动打标结果默认使用 `tag` 作为输出列名，除非 xattr 元数据另有定义。
3. 结果文件调用 `write_meta()` 写入 xattr。
4. 自动打标完成后回写：
   - 标签列
   - 标签名字
   - 规则名
   - 规则版本

### 5.6 训练文件接口（新增）

提供以下接口供大模型训练模块调用：

1. **`GET /api/v1/training/files`**：
   - 启动时扫描文件系统的 xattr 元数据，构建内存索引
   - 支持按 categoryId、tag、hasLabel、keyword 筛选、分页和排序
   - **响应中剥离 `storagePath`**，只返回文件元数据摘要

2. **`POST /api/v1/training/submit`**：
   - 接收 `selectedFileIds` 数组
   - 内部通过 `_path_map` 解析 fileId → storagePath
   - 校验文件存在且可读后启动训练，返回 taskId

3. **`GET /api/v1/training/tasks/{taskId}`**：
   - 返回训练进度、已处理文件数、错误信息

4. **安全约束**：
   - 元数据以加密形式存储在文件 xattr 中，磁盘上无独立配置文件
   - 所有接口需 JWT 认证
   - `storagePath` 永不出现在任何 API 响应中
   - 记录所有访问和提交审计日志
