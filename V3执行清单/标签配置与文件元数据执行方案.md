# V3 执行清单：标签配置与文件元数据方案

## 1. 目标

为每个文件引入独立配置文件，统一记录文件来源、是否含标签、标签列、标签名字、可用标签范围、处理方式和存放目录，确保数据库导出、文件上传、预览编辑、手动打标、自动打标都能基于同一套元数据运行。

## 2. 需求范围

### 2.1 必须支持的场景

1. 数据库导出时，用户必须填写：
   - 是否含标签
   - 若含标签：标签列
   - 标签名字
   - 若不含标签：候选标签范围
2. 文件上传时，用户必须填写：
   - 是否含标签
   - 若含标签：标签列
   - 标签名字
   - 若不含标签：候选标签范围
3. 对已有文件进行手动打标签或自动打标签后，网站必须回写配置文件，记录：
   - 标签列
   - 标签名字
   - 结果文件目录
   - 处理方式
4. 无标签文件正常放入普通目录，有标签文件放入标签目录。
5. 文件预览编辑区新增字段最多只允许新增 1 列，且列名固定为 tag。
6. 自动打标签支持按多列组合规则配置“根据哪些列打什么标签”。

### 2.2 约束

1. 配置文件与文件必须一一对应。
2. 配置文件中凡是出现“标签列”的地方，都必须同步写入“标签名字”。
3. 无标签文件的配置文件必须写入候选标签范围，后续手动标签只能从该范围中选择。
4. 有标签文件的配置文件必须写入标签列、标签名字，并保留来源信息。

## 3. 配置文件建议结构

每个文件旁边生成一个同名配置文件，例如：

- `sample.csv`
- `sample.csv.meta.json`

### 3.1 建议字段

```json
{
  "fileId": "file_001",
  "fileName": "sample.csv",
  "sourceType": "db_export | upload | manual_tag | auto_tag",
  "storageType": "plain | tagged",
  "storagePath": "/path/to/file",
  "hasTag": true,
  "tagColumn": "tag",
  "tagName": "标签名称",
  "tagRange": ["故障", "预警", "正常"],
  "tagStrategy": "column_tag | manual_range | auto_rule",
  "tagRule": {
    "ruleName": "按设备类型和状态打标",
    "inputs": ["device_type", "status"],
    "mapping": [
      { "when": { "device_type": "A", "status": "bad" }, "tag": "故障" }
    ]
  },
  "createdAt": "2026-05-22T10:00:00+08:00",
  "updatedAt": "2026-05-22T10:00:00+08:00"
}
```

### 3.2 规则

1. `hasTag = true` 时，必须存在 `tagColumn` 和 `tagName`。
2. `hasTag = false` 时，必须存在 `tagRange`。
3. 如果文件经过手动/自动打标生成新文件，必须生成新配置文件并继承必要元数据。
4. 如果是普通目录文件，但后续被打标进入标签目录，则配置文件中的 `storageType` 需要同步更新。

## 4. 前端改造清单

### 4.1 数据库导出页面

1. 增加“是否含标签”选项。
2. 若选择“是”，显示：
   - 标签列输入框
   - 标签名字输入框
3. 若选择“否”，显示：
   - 候选标签范围输入框
4. 导出提交时，把这些字段一并提交给后端。
5. 导出成功后，前端需显示配置文件写入结果。

### 4.2 文件上传页面

1. 增加“是否含标签”选项。
2. 若选择“是”，显示：
   - 标签列输入框
   - 标签名字输入框
3. 若选择“否”，显示：
   - 候选标签范围输入框
4. 提交上传时，一并提交标签元数据。
5. 上传完成后，前端应提示文件配置文件位置。

### 4.3 文件预览编辑区

1. 预览区域新增字段按钮最多只能使用一次。
2. 新增字段列名固定为 `tag`。
3. 如果当前文件已有 `tag` 列，则禁止再新增。
4. 保存前要校验：
   - 新增列不得超过 1 列
   - 新列名必须是 `tag`
5. 若文件原本已有标签列，展示时应优先读取配置文件中的 `tagColumn` 和 `tagName`。

### 4.4 自动打标签页面

1. 标签规则支持多列输入。
2. 页面需要支持配置：
   - 参与打标的列
   - 每列对应的规则
   - 输出标签名
3. 规则保存后写入配置文件或规则存储区。

### 4.5 在文件预览内集成自动打标签（新增）

1. 目的：将“自动打标签”入口直接放到文件预览区（即手动打标签下方），允许用户在不手动填写 `fileId` 的情况下，直接对当前选中的文件执行自动打标。
2. 交互说明：
   - 自动打标按钮放在预览编辑区（与“保存标签”同组或紧邻），默认禁用，只有当用户在“文件中心”选中某个文件并在预览区打开时才可用。
   - 若没有选中文件，支持显示一个“请选择文件”提示或提供高级模式输入框，允许手动输入 `fileId` 作为兜底。
   - 点击自动打标前，前端应向后端传递当前的 `fileId`（来自 `selectedFileId` 状态）、选定的 `tagRule`（或使用默认规则）、以及可选的 `tagColumn`/`tagName` 覆盖参数。
3. 技术可行性：
   - 现有前端已经维护 `selectedFileId` 状态（见 `v1-frontend/app.js` 中的 `state.selectedFileId`），预览接口和打标接口均以 `fileId` 为目标，因而该改造无需新增后端接口。
   - 前端只需把自动打标按钮的触发逻辑改为使用 `state.selectedFileId`，并保持现有调用 `/api/v1/tags/auto` 的请求格式即可。
4. 校验与安全：
   - 点击自动打标时校验 `selectedFileId` 非空并且该文件存在；若配置文件中声明了 `tagColumn` 或 `tagRange`，应先校验规则与目标一致性（例如不存在冲突的 `tagColumn`）。
   - 若自动打标需要写入 `tag` 列且该列已存在且不可覆盖，则须提示用户确认或失败退出。
5. 用户体验建议：
   - 默认隐藏单独的 `fileId` 文本框，仅在用户切换到“高级模式”或未选中文件时显示。
   - 自动打标执行后在预览区域显示执行结果摘要，并提示生成的配置文件位置与新文件路径。


## 5. 后端改造清单

### 5.1 导出接口

1. 扩展导出请求参数，接收：
   - `hasTag`
   - `tagColumn`
   - `tagName`
   - `tagRange`
2. 导出结果写入文件后，同时写入 `.meta.json` 配置文件。
3. 若 `hasTag = true`，必须校验 `tagColumn` 和 `tagName` 非空。
4. 若 `hasTag = false`，必须校验 `tagRange` 非空。

### 5.2 上传接口

1. 扩展上传请求参数，接收：
   - `hasTag`
   - `tagColumn`
   - `tagName`
   - `tagRange`
2. 写入普通目录或标签目录时，同时生成配置文件。
3. 标签文件进入标签目录，普通文件进入普通目录。
4. 上传后文件的配置文件必须可被文件列表和预览接口读取。

### 5.3 预览接口

1. 预览接口优先读取配置文件。
2. 如果配置文件声明了 `tagColumn`，预览输出要识别该列。
3. 如果文件无标签，但允许新增标签列，则新增列名只能是 `tag`。
4. 预览返回值里建议附带配置文件摘要：
   - `hasTag`
   - `tagColumn`
   - `tagName`
   - `tagRange`

### 5.4 手动打标签接口

1. 校验标签值必须来自配置文件中的候选标签范围。
2. 输出文件后写入新的配置文件。
3. 配置文件中必须记录最终标签列和标签名字。
4. 若新增了 `tag` 列，必须同步更新文件元数据。

### 5.5 自动打标签接口

1. 扩展规则结构，支持多列条件。
2. 自动打标结果默认使用 `tag` 作为输出列名，除非配置文件另有定义。
3. 结果文件与配置文件一起落盘。
4. 自动打标完成后回写：
   - 标签列
   - 标签名字
   - 规则名
   - 规则版本

## 6. 文件目录规则

1. 无标签文件：
   - 进入普通目录
   - 配置文件中写入 `hasTag = false`
   - 必须写入 `tagRange`
2. 有标签文件：
   - 进入标签目录
   - 配置文件中写入 `hasTag = true`
   - 必须写入 `tagColumn` 和 `tagName`
3. 打标后的结果文件：
   - 进入标签目录
   - 配置文件中同步写入最终标签信息

## 7. 验收标准

### 7.1 功能验收

1. 数据库导出时可以填写是否含标签、标签列、标签名字或候选标签范围。
2. 文件上传时可以填写是否含标签、标签列、标签名字或候选标签范围。
3. 每个文件都有独立配置文件。
4. 无标签文件的配置文件里有候选标签范围。
5. 有标签文件的配置文件里有标签列和标签名字。
6. 预览新增字段最多只能新增一列，且列名固定为 `tag`。
7. 自动打标签可按多列规则配置。
8. 打标后的文件会正确进入标签目录。

### 7.2 校验验收

1. 配置文件缺少 `tagColumn` 或 `tagName` 时，有标签文件应拒绝保存。
2. 无标签文件缺少 `tagRange` 时，应拒绝保存。
3. 预览编辑区新增超过 1 列时，应前端和后端同时拦截。
4. 自动打标规则缺少输入列或输出标签时，应提示错误。

## 8. 推荐实施顺序

### 第 1 步：定义配置文件 schema
- 先统一字段名和文件命名规则。
- 明确 `hasTag`、`tagColumn`、`tagName`、`tagRange`、`storageType` 的含义。

### 第 2 步：改前端导出/上传表单
- 增加是否含标签、标签列、标签名字、标签范围。
- 把参数传给后端。

### 第 3 步：改后端导出/上传接口
- 接收并校验新参数。
- 写文件时同步生成配置文件。

### 第 4 步：改预览与打标逻辑
- 预览编辑区限制为 1 列 tag。
- 手动/自动打标结果同步写配置文件。

### 第 5 步：补规则校验与测试
- 增加配置文件完整性校验。
- 增加导出、上传、预览、打标的回归测试。

## 9. 当前可行性结论

1. 方案可行。
2. 现有项目已经具备文件流转、预览、打标、目录管理基础。
3. 主要工作量在于：
   - 元数据配置文件体系
   - 前端表单扩展
   - 后端参数校验
   - 预览 tag 列约束
   - 自动打标多列规则化

## 10. 待确认点

1. “标签名字”是否等同于标签列的人类可读名称，还是标签类别名。
2. “标签范围”是否只用于无标签文件的手动打标候选值。
3. 配置文件是要跟随原文件同目录，还是统一放到旁路目录。
4. 预览新增的 `tag` 列，是覆盖已有列还是只在不存在时补充。
