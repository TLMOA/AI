# V3 执行清单：标签配置与文件元数据方案（文件配置版）

## 1. 目标

为每个数据文件配套一个独立的配置信息文件，统一记录文件来源、是否含标签、标签列、标签名字、可用标签范围、处理方式和存放目录，确保数据库导出、文件上传、预览编辑、手动打标、自动打标都能基于同一套文件级配置运行。

## 2. 需求范围

### 2.1 必须支持的场景

1. 数据库导出时，用户必须填写：
   - 是否含标签
   - 若含标签：标签列
   - 标签名字
   - 若不含标签：候选标签范围
2. 文件上传时，用户必须填写：
   - 是否含标签
   - 若含标签：标签列
   - 标签名字
   - 若不含标签：候选标签范围
3. 对已有文件进行手动打标签或自动打标签后，网站必须回写配置信息文件，记录：
   - 标签列
   - 标签名字
   - 结果文件目录
   - 处理方式
4. 无标签文件正常放入普通目录，有标签文件放入标签目录。
5. 文件预览编辑区新增字段最多只允许新增 1 列，且列名固定为 `tag`。
6. 自动打标签支持按多列组合规则配置“根据哪些列打什么标签”。

### 2.2 约束

1. 每个数据文件都必须配套一个独立的配置文件。
2. 配置信息文件与数据文件一一对应，采用同名 sidecar 形式存放。
3. 元数据中凡是出现“标签列”的地方，都必须同步写入“标签名字”。
4. 无标签文件的配置信息必须写入候选标签范围，后续手动标签只能从该范围中选择。
5. 有标签文件的配置信息必须写入标签列、标签名字，并保留来源信息。

## 3. 元数据存储方案：数据文件 + 独立配置文件

### 设计理念

**磁盘上同时存在数据文件和配套配置文件**。配置信息采用普通 JSON 文件保存，不使用扩展属性，也不做额外加密处理。文件与配置文件按同名规则配对，便于人工排查、备份恢复和跨平台处理。

```
传统方案：
  sensor_data.csv              ← 数据文件
  sensor_data.csv.meta.json    ← 配置文件（独立存在）

本方案：
  sensor_data.csv
  sensor_data.csv.meta.json    ← 与数据文件同名配套
```

**关键特性**：

| 特性 | 说明 |
|------|------|
| 一文件一配置 | 每个数据文件都有一个独立的配套配置文件 |
| 同名配对 | 配置文件与数据文件保持相同主文件名，便于定位 |
| 跨平台友好 | Linux、macOS、Windows 都可直接使用 |
| 可读可查 | 运维、测试、人工排障时可直接查看 JSON 内容 |
| 实现简单 | 直接使用标准文件读写即可，不依赖特殊文件系统能力 |

### 3.1 配置文件格式

字段定义与原 `.meta.json` 方案一致，不增不减，直接保存为普通 JSON 文件：

```json
{
  "fileId": "file_d29b73dd23",
  "fileName": "sensor_data.csv",
  "sourceType": "db_export | upload | manual_tag | auto_tag",
  "storageType": "plain | tagged",
  "storagePath": "/home/yhz/nifi-data/output_csv/sensor_data.csv",
  "hasTag": false,
  "tagColumn": "tag",
  "tagName": "标签名称",
  "tagRange": ["故障", "预警", "正常"],
  "failedTag": "故障",
  "tagStrategy": "column_tag | manual_range | auto_rule",
  "tagRule": {
    "ruleName": "按设备类型和状态打标",
    "inputs": ["device_type", "status"],
    "mapping": [
      { "when": { "device_type": "A", "status": "bad" }, "tag": "故障" }
    ]
  },
  "trainable": true,
  "categoryId": "cat_002",
  "categoryName": "传感器数据",
  "description": "2026年5月传感器采集数据",
  "columns": ["device_id", "temperature", "humidity", "timestamp"],
  "rowCount": 12500,
  "fileSize": 1048576,
  "createdAt": "2026-05-22T10:00:00+08:00",
  "updatedAt": "2026-05-22T10:00:00+08:00"
}
```

#### 字段说明（含来源标注）

> **自动**：系统写入，无需用户操作。**用户**：需用户在对应页面上填写/选择。

| 字段 | 类型 | 必须 | 来源 | 说明 |
|------|------|:--:|:--:|------|
| `fileId` | string | 是 | 自动 | 系统根据文件路径 + 时间戳生成唯一标识，用户不可见 |
| `fileName` | string | 是 | 自动 | 从数据文件的实际文件名读取，用户不可修改 |
| `sourceType` | string | 是 | 自动 | 系统根据触发入口自动写入：`db_export` / `upload` / `manual_tag` / `auto_tag` |
| `storageType` | string | 是 | 自动 | 系统根据 `hasTag` 和落盘目录自动写入：有标签文件 → `tagged`，无标签文件 → `plain` |
| `storagePath` | string | 是 | 自动 | 文件落盘时系统自动记录绝对路径，后端内部使用，API 响应中不直接返回 |
| `hasTag` | boolean | 是 | 用户 | 导出/上传时用户选择：该文件中是否已经包含标签列 |
| `tagColumn` | string | 条件 | 用户 | `hasTag=true` 时必填，用户指定文件中哪一列是标签列 |
| `tagName` | string | 条件 | 用户 | `hasTag=true` 时必填，标签列的人类可读名称，用于页面展示 |
| `tagRange` | array | 条件 | 用户 | `hasTag=false` 时必填，用户指定候选标签范围 |
| `failedTag` | string | 条件 | 用户 | `hasTag=false` 时必填，指定 `tagRange` 中哪个标签代表故障/最差状态 |
| `tagStrategy` | string | 否 | 自动 | 系统根据操作入口写入：导出/上传已有标签 → `column_tag`，手动打标 → `manual_range`，自动打标 → `auto_rule` |
| `tagRule` | object | 否 | 用户 | 仅在自动打标时由用户配置，定义参与打标的列、条件和输出标签 |
| `trainable` | boolean | 否 | 自动 | 系统默认 `true`，表示该文件可用于模型训练 |
| `categoryId` | string | 否 | 自动+用户 | 系统根据文件来源目录自动归类，用户可在页面上修改 |
| `categoryName` | string | 否 | 自动+用户 | 与 `categoryId` 对应的人类可读名称，系统根据目录预设，用户可改 |
| `description` | string | 否 | 用户 | 可选的文件描述文本，由用户在导出/上传/预览页面填写 |
| `columns` | array | 否 | 自动 | 系统读取文件第一行自动解析列名列表 |
| `rowCount` | number | 否 | 自动 | 系统统计文件数据行数（不含表头） |
| `fileSize` | number | 否 | 自动 | 系统通过 `os.path.getsize()` 自动获取（单位：字节） |
| `createdAt` | string | 是 | 自动 | 文件首次生成时系统写入 ISO 8601 时间戳 |
| `updatedAt` | string | 是 | 自动 | 每次配置文件内容变更时系统自动更新 ISO 8601 时间戳 |

#### 3.1.1 各场景字段来源汇总

> 同一字段在不同场景下来源不同，下表按场景拆分。

| 字段 | 数据库导出 | 文件上传 | 手动打标 | 自动打标 |
|------|:--:|:--:|:--:|:--:|
| `fileId` | 自动 | 自动 | 自动 | 自动 |
| `fileName` | 自动 | 自动 | 自动 | 自动 |
| `sourceType` | `db_export` | `upload` | `manual_tag` | `auto_tag` |
| `storageType` | 自动 | 自动 | 自动 | 自动 |
| `storagePath` | 自动 | 自动 | 自动 | 自动 |
| `hasTag` | 用户选择 | 用户选择 | 自动→`true` | 自动→`true` |
| `tagColumn` | 用户输入† | 用户输入† | 自动→`"tag"` | 自动→`"tag"` |
| `tagName` | 用户输入† | 用户输入† | 用户输入 | 用户输入 |
| `tagRange` | 用户输入‡ | 用户输入‡ | 继承原文件 | — |
| `failedTag` | 用户输入‡ | 用户输入‡ | 继承原文件 | — |
| `tagStrategy` | 自动 | 自动 | `manual_range` | `auto_rule` |
| `tagRule` | — | — | — | 用户配置 |
| `columns` | 自动 | 自动 | 自动 | 自动 |
| `rowCount` | 自动 | 自动 | 自动 | 自动 |
| `fileSize` | 自动 | 自动 | 自动 | 自动 |

> † 仅 `hasTag=true` 时显示并必填。  
> ‡ 仅 `hasTag=false` 时显示并必填。  
> `—` 表示该场景下不产生此字段。

### 3.2 规则

1. `hasTag = true` 时，必须存在 `tagColumn` 和 `tagName`。
2. `hasTag = false` 时，必须存在 `tagRange` 和 `failedTag`。
3. 如果文件经过手动/自动打标生成新文件，必须对新文件写入配套配置文件并继承必要字段。
4. 如果是普通目录文件，但后续被打标进入标签目录，则配置文件中的 `storageType` 需要同步更新。
5. `failedTag` 必须是 `tagRange` 数组中的元素。

### 3.3 配置文件读写实现

#### 3.3.1 文件结构设计

配套配置文件建议使用以下命名规则：

- 数据文件：`sensor_data.csv`
- 配置文件：`sensor_data.csv.meta.json`

这种方式的好处是：

- 只看文件名就能知道对应关系
- 方便人工编辑、脚本处理、备份恢复
- 不需要特殊文件系统能力

#### 3.3.2 核心代码

```python
import json
import os
from pathlib import Path

META_SUFFIX = ".meta.json"


def meta_path(file_path: str) -> str:
    return f"{file_path}{META_SUFFIX}"


def write_meta(file_path: str, meta: dict) -> None:
    """将元数据写入与数据文件同名的配置文件。"""
    path = Path(meta_path(file_path))
    path.write_text(json.dumps(meta, ensure_ascii=False, indent=2), encoding="utf-8")


def read_meta(file_path: str) -> dict:
    """读取配套配置文件中的元数据。"""
    path = Path(meta_path(file_path))
    if not path.exists():
        raise FileNotFoundError(f"配置文件不存在: {path}")
    return json.loads(path.read_text(encoding="utf-8"))


def has_meta(file_path: str) -> bool:
    """检查文件是否存在配套配置文件。"""
    return Path(meta_path(file_path)).exists()


def delete_meta(file_path: str) -> None:
    """删除配套配置文件。"""
    path = Path(meta_path(file_path))
    if path.exists():
        path.unlink()
```

#### 3.3.3 配置文件同步规则

| 场景 | 处理方式 |
|------|------|
| 文件创建 | 数据文件写入后立即创建对应 `.meta.json` |
| 文件更新 | 配置内容变更时覆盖写入 `.meta.json` |
| 文件改名 | 数据文件改名时同步重命名 `.meta.json` |
| 文件移动 | 数据文件移动时同步移动 `.meta.json` |
| 文件删除 | 数据文件删除时同步删除 `.meta.json` |

#### 3.3.4 开发环境处理

Linux、macOS、Windows 全部统一使用同一套 `.meta.json` 文件，不再区分扩展属性与降级方案。

### 3.4 训练文件元数据方案

> **定位说明**：本模块不负责训练文件选取的前端界面，选取交互由大模型团队在另一个模块独立实现。这里仅提供标准化的文件级配置结构和按需读取接口，供下游模块调用。

#### 3.4.1 设计原则

- **配置文件是唯一来源**：每个数据文件的元数据保存在对应的 `.meta.json` 中。
- **路径隔离**：`storagePath` 仅在后端内部使用，API 响应中不包含此字段，下游模块通过 `fileId` 间接引用实际文件。
- **按需读取，不做全局聚合**：不构建统一的内存索引，查询时直接遍历目标目录并读取对应配置文件。

#### 3.4.2 目录结构与文件布局

```

数据存储 (Web 不可访问):
  /home/yhz/nifi-data/
  ├── exports/                                   ← 用户数据库导出（按 用户名/任务名 组织）
  │   ├── admin/16/job_16_sensor_data_20260421_102049.csv
  │   └── user-001/1/job_1_iot_users_20260413_103205.json
  ├── inbox_tsv/                                 ← 用户上传的 TSV 文件
  │   └── acc_0f6da7b5_sample.tsv
  ├── output_csv/                                ← CSV 格式输出（无标签）
  │   ├── sensor_data.csv
  │   └── sensor_data.csv.meta.json
  │   └── tagged_output/                         ← CSV 输出（有标签）
  │       ├── sensor_tagged_20260330_040356397.csv
  │       └── sensor_tagged_20260330_040356397.csv.meta.json
  └── output_json/                               ← JSON 格式输出
      ├── sensor_data.jsonl

```

> 每个文件都有独立的 `.meta.json` 配套文件。训练模块和业务模块只需通过 API 查询或按需读取，无需依赖额外索引服务。

#### 3.4.3 读取策略

后端在处理请求时，按需遍历指定目录并读取配套配置文件：

```python
from pathlib import Path


def iter_data_files(base_dir: str):
    for file_path in Path(base_dir).rglob("*"):
        if not file_path.is_file():
            continue
        if str(file_path).endswith(".meta.json"):
            continue
        if not has_meta(str(file_path)):
            continue
        yield file_path, read_meta(str(file_path))
```

- **列表查询**：请求到来时遍历目标目录，读取符合条件的文件及其 `.meta.json`。
- **单文件操作**：通过当前文件路径直接定位配套配置文件。
- **不建立全局聚合索引**：不维护跨请求的统一内存目录表。

#### 3.4.5 安全隔离方案

核心要求：元数据不再隐藏在特殊文件系统能力中，而是通过目录权限、API 认证和响应字段控制来隔离。

**四层隔离**：

```
任何人（包括 SSH 登录的开发运维人员）
    │
    ▼ ls /home/yhz/nifi-data/output_csv/
┌──────────────────────────────┐
│  磁盘上有数据文件和配套配置文件  │  → 结构清晰但受目录权限保护
│  sensor_data.csv             │
│  sensor_data.csv.meta.json   │
└──────────────────────────────┘
    │
    ▼ cat sensor_data.csv
┌──────────────────────────────┐
│  文件内容正常                   │  → 只看见数据内容
│  device_id,temperature,...   │
└──────────────────────────────┘
    │
    ▼ cat sensor_data.csv.meta.json
┌──────────────────────────────┐
│  看到完整 JSON 配置             │  → 需要文件权限控制访问
│  fileId / tagRange / tagRule   │
└──────────────────────────────┘
    │
    ▼ 浏览器 / API 调用（唯一合法路径）
┌──────────────────────────────┐
│  Nginx + JWT 认证 + API      │  → 仅返回元数据摘要，不含 storagePath
│  响应中不含真实路径             │
└──────────────────────────────┘
```

**攻击面评估**：

| 攻击方式 | 结果 |
|----------|------|
| 浏览器 URL 访问 | ❌ Nginx 不暴露数据目录 |
| API 调用 | ❌ 响应不含 `storagePath` |
| SSH `ls` / `cat` | ⚠️ 需要目录权限控制，不能靠隐藏属性 |
| 文件系统备份 | ⚠️ 需同时备份数据文件和 `.meta.json` |
| 物理硬盘窃取 | ⚠️ 依赖磁盘加密或主机权限边界 |

**文件操作注意事项**：

| 操作 | 正确方式 | 错误方式 |
|------|------|------|
| 复制文件 | `cp src dst` 后同步复制 `.meta.json` | 只复制数据文件 |
| 同步 | `rsync -a src dst` 并包含 `.meta.json` | 只同步数据文件 |
| 打包 | `tar -cf arch.tar files/` 时同时打包 `.meta.json` | 漏掉配置文件 |
| 文件改名 | 数据文件与 `.meta.json` 同步改名 | 只改数据文件名 |

#### 3.4.6 配置管理

**版本控制**：
- 修改元数据前，先将当前 `.meta.json` 导出到备份文件
- 保留最近 5 个备份版本，超出自动清理
- 变更记录写入审计日志

**更新机制**：
- 数据文件与配置文件由同一后端事务保证一致性
- 下游模块调用 `/api/v1/training/files` 时按需读取到的始终是最新数据
- 不维护跨请求的统一索引表，避免缓存过期问题

**备份策略**：

| 类型 | 频率 | 保留 | 内容 |
|------|------|------|------|
| 实时备份 | 每次修改前 | 5 个版本 | 单个文件 `.meta.json` 的备份 |
| 每日全量 | 每天 02:00 | 30 天 | 数据文件 + `.meta.json` 全量打包 |

**从旧方案迁移**（已有项目一次性执行）：

```python
from pathlib import Path
import json


def migrate_all(base_dir: str):
    """一次性将存量元数据迁移为 .meta.json 配置文件。"""
    base = Path(base_dir)
    for data_path in base.rglob("*"):
        if not data_path.is_file():
            continue
        if str(data_path).endswith(".meta.json"):
            continue
        meta_path = Path(str(data_path) + ".meta.json")
        if meta_path.exists():
            continue
        meta = build_meta_from_existing_data(str(data_path))
        meta_path.write_text(json.dumps(meta, ensure_ascii=False, indent=2), encoding="utf-8")
```

## 4. 前端改造清单

### 4.1 数据库导出页面

1. 增加“是否含标签”选项。
2. 若选择“是”，显示：

   - 候选标签范围输入框
4. 导出提交时，把这些字段一并提交给后端。
5. 导出成功后，前端需显示配置文件写入结果和 `.meta.json` 路径。

### 4.2 文件上传页面

1. 增加“是否含标签”选项。
2. 若选择“是”，显示：
   - 标签列输入框
   - 标签名字输入框
3. 若选择“否”，显示：
   - 候选标签范围输入框
4. 提交上传时，一并提交标签元数据。
5. 上传完成后，前端应提示文件配置文件位置。

### 4.3 文件预览编辑区

1. 预览区域新增字段按钮最多只能使用一次。
2. 新增字段列名固定为 `tag`。
3. 如果当前文件已有 `tag` 列，则禁止再新增。
4. 保存前要校验：
   - 新增列不得超过 1 列
   - 新列名必须是 `tag`
5. 若文件原本已有标签列，展示时应优先读取 `.meta.json` 中的 `tagColumn` 和 `tagName`。

### 4.4 自动打标签页面

1. 标签规则支持多列输入。
2. 页面需要支持配置：
   - 参与打标的列
   - 每列对应的规则
   - 输出标签名
3. 规则保存后写入配置文件。

### 4.5 在文件预览内集成自动打标签（新增）

1. 目的：将“自动打标签”入口直接放到文件预览区（即手动打标签下方），允许用户在不手动填写 `fileId` 的情况下，直接对当前选中的文件执行自动打标。
2. 交互说明：
   - 自动打标按钮放在预览编辑区（与“保存标签”同组或紧邻），默认禁用，只有当用户在“文件中心”选中某个文件并在预览区打开时才可用。
   - 若没有选中文件，支持显示一个“请选择文件”提示或提供高级模式输入框，允许手动输入 `fileId` 作为兜底。
   - 点击自动打标前，前端应向后端传递当前的 `fileId`（来自 `selectedFileId` 状态）、选定的 `tagRule`（或使用默认规则）、以及可选的 `tagColumn`/`tagName` 覆盖参数。
3. 技术可行性：
   - 现有前端已经维护 `selectedFileId` 状态，预览接口和打标接口均以 `fileId` 为目标，因而该改造无需新增后端接口。
   - 前端只需把自动打标按钮的触发逻辑改为使用 `state.selectedFileId`，并保持现有调用 `/api/v1/tags/auto` 的请求格式即可。
4. 校验与安全：
   - 点击自动打标时校验 `selectedFileId` 非空并且该文件存在；若配置文件中声明了 `tagColumn` 或 `tagRange`，应先校验规则与目标一致性。
   - 若自动打标需要写入 `tag` 列且该列已存在且不可覆盖，则须提示用户确认或失败退出。
5. 用户体验建议：
   - 默认隐藏单独的 `fileId` 文本框，仅在用户切换到“高级模式”或未选中文件时显示。
   - 自动打标执行后在预览区域显示执行结果摘要，并提示生成的配置文件位置与新文件路径。

## 5. 后端改造清单

### 5.1 导出接口

1. 扩展导出请求参数，接收：
   - `hasTag`
   - `tagColumn`
   - `tagName`
   - `tagRange`
2. 导出结果写入文件后，调用 `write_meta()` 将元数据写入该文件的配套 `.meta.json`。
3. 若 `hasTag = true`，必须校验 `tagColumn` 和 `tagName` 非空。
4. 若 `hasTag = false`，必须校验 `tagRange` 非空。

### 5.2 上传接口

1. 扩展上传请求参数，接收：
   - `hasTag`
   - `tagColumn`
   - `tagName`
   - `tagRange`
2. 写入普通目录或标签目录时，调用 `write_meta()` 将元数据写入配套 `.meta.json`。
3. 标签文件进入标签目录，普通文件进入普通目录。
4. 上传后文件的元数据必须可被 `has_meta()` + `read_meta()` 读取。

### 5.3 预览接口

1. 预览接口通过 `read_meta()` 读取文件配套 `.meta.json`。
2. 如果元数据声明了 `tagColumn`，预览输出要识别该列。
3. 如果文件无标签，但允许新增标签列，则新增列名只能是 `tag`。
4. 预览返回值里附带元数据摘要：
   - `hasTag`
   - `tagColumn`
   - `tagName`
   - `tagRange`

### 5.4 手动打标签接口

1. 校验标签值必须来自元数据中的候选标签范围。
2. 输出文件后通过 `write_meta()` 写入新文件的配套 `.meta.json`。
3. 元数据中必须记录最终标签列和标签名字。
4. 若新增了 `tag` 列，必须同步更新配套配置文件。

### 5.5 自动打标签接口

1. 扩展规则结构，支持多列条件。
2. 自动打标结果默认使用 `tag` 作为输出列名，除非配置文件另有定义。
3. 结果文件调用 `write_meta()` 写入配套 `.meta.json`。
4. 自动打标完成后回写：
   - 标签列
   - 标签名字
   - 规则名
   - 规则版本

### 5.6 训练文件接口（新增）

提供以下接口供大模型训练模块调用：

1. **`GET /api/v1/training/files`**：
   - 请求到来时遍历目录并读取配套 `.meta.json`
   - 支持按 categoryId、tag、hasLabel、keyword 筛选、分页和排序
   - **响应中剥离 `storagePath`**，只返回文件元数据摘要

2. **`POST /api/v1/training/submit`**：
   - 接收 `selectedFileIds` 数组
   - 内部通过文件遍历匹配 fileId，再解析 storagePath
   - 校验文件存在且可读后启动训练，返回 taskId

3. **`GET /api/v1/training/tasks/{taskId}`**：
   - 返回训练进度、已处理文件数、错误信息

4. **安全约束**：
   - 元数据保存在文件配套 `.meta.json` 中
   - 所有接口需 JWT 认证
   - `storagePath` 永不出现在任何 API 响应中
   - 记录所有访问和提交审计日志

## 6. 文件目录规则

1. 无标签文件：
   - 进入普通目录
   - 配套 `.meta.json` 中写入 `hasTag = false`
   - 必须写入 `tagRange`
2. 有标签文件：
   - 进入标签目录
   - 配套 `.meta.json` 中写入 `hasTag = true`
   - 必须写入 `tagColumn` 和 `tagName`
3. 打标后的结果文件：
   - 进入标签目录
   - 配套 `.meta.json` 中同步写入最终标签信息

## 7. 验收标准

### 7.1 功能验收

1. 数据库导出时可以填写是否含标签、标签列、标签名字或候选标签范围。
2. 文件上传时可以填写是否含标签、标签列、标签名字或候选标签范围。
3. 每个文件都有一个独立的 `.meta.json` 配套文件。
4. 无标签文件的配套配置里有候选标签范围。
5. 有标签文件的配套配置里有标签列和标签名字。
6. 预览新增字段最多只能新增一列，且列名固定为 `tag`。
7. 自动打标签可按多列规则配置。
8. 打标后的文件会正确进入标签目录。

### 7.2 校验验收

1. 元数据缺少 `tagColumn` 或 `tagName` 时，有标签文件应拒绝保存。
2. 无标签文件缺少 `tagRange` 时，应拒绝保存。
3. 预览编辑区新增超过 1 列时，应前端和后端同时拦截。
4. 自动打标规则缺少输入列或输出标签时，应提示错误。
