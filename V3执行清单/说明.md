## 先搞懂基础：inode 扩展属性到底是什么

### 一个文件在 Linux 磁盘上的真实结构

```
sensor_data.csv 这个文件，在磁盘上由两部分组成：

┌──────────────────────────────────────────────┐
│                  inode 表                     │
│  ┌────────────────────────────────────────┐  │
│  │ inode #528491                          │  │
│  │                                        │  │
│  │ 文件类型: 普通文件                       │  │
│  │ 权限:     rw-r----- (640)              │  │
│  │ 所有者:   yhz                           │  │
│  │ 文件大小: 1048576 字节                   │  │
│  │ 创建时间: 2026-05-22 10:00              │  │
│  │ 修改时间: 2026-05-25 16:30              │  │
│  │                                        │  │
│  │ ★ 扩展属性区（xattr）                    │  │
│  │ ┌────────────────────────────────────┐ │  │
│  │ │ user.meta     = "eUp4V09FS2..."    │ │  │
│  │ │ user.checksum = "abc123def..."     │ │  │
│  │ └────────────────────────────────────┘ │  │
│  │                                        │  │
│  │ ★ 数据块指针                           │  │
│  │ → 块 #12001                            │  │
│  │ → 块 #12002                            │  │
│  │ → 块 #12003                            │  │
│  └────────────────────────────────────────┘  │
└──────────────────────────────────────────────┘

┌──────────────────────────────────────────────┐
│                  数据块区                      │
│  ┌────────────────────────────────────────┐  │
│  │ 块 #12001:                             │  │
│  │ device_id,temperature,timestamp,status │  │
│  │ 001,25.6,2026-05-25T10:00:00Z,normal  │  │
│  │ 002,31.2,2026-05-25T10:01:00Z,fault   │  │
│  │ ...                                    │  │
│  └────────────────────────────────────────┘  │
└──────────────────────────────────────────────┘
```

**关键结论**：

| 操作 | 看到的是什么 |
|------|------------|
| `cat sensor_data.csv` | 只读数据块区的文件内容 |
| `ls -la sensor_data.csv` | 只读 inode 的基本信息（权限、大小、时间） |
| `getfattr -d sensor_data.csv` | 才能读 inode 的扩展属性区 |
| 文件管理器 | 同 `ls`，看不到扩展属性 |

**xattr 不属于文件内容。** `cat` 输出里不会多任何东西，文件大小不增加，复制时默认也不会保留。它是藏在 inode 深处的一小块附加空间，99% 的用户甚至不知道它的存在。

### `user.meta` 和 `user.checksum` 是什么

`user.` 是 Linux 对用户自定义扩展属性强制要求的**命名空间前缀**，就像域名一样防止冲突。不是指"系统用户"。

```
user.meta      → 一条扩展属性，key="user.meta"，value=加密后的元数据密文
user.checksum  → 一条扩展属性，key="user.checksum"，value=SHA-256 校验码（明文）
```

为什么需要 `user.checksum`？解密后用它验证数据没有被磁盘故障或人为破坏篡改过——解密成功不等于数据是对的，但对上 checksum 就一定是原始的。

## 回答你的三个问题

### 1. 配置信息到底怎么存放的？

```
数据文件 sensor_data.csv 在磁盘上：

  ┌─ 数据块：CSV 文本，这就是 cat 看到的东西
  │  device_id,temperature,timestamp
  │  001,25.6,2026-05-25T10:00:00Z
  │
  ├─ inode 基本属性：权限、大小、时间，这是 ls -la 看到的东西
  │  -rw-r----- 1 yhz yhz  1048576  May 25 10:00 sensor_data.csv
  │
  └─ inode 扩展属性 (xattr)：被加密的配置信息，ls/cat 都看不到
     user.meta     = "eUp4V09FS2hpQ0lPM1VuQzZZcHRaR2x6ZEdGeV..."  ← AES-256-GCM 密文
     user.checksum = "a1b2c3d4e5f6..."                              ← SHA-256 校验码
```

- **`user.meta`**：key 叫 "user.meta"，value 是完整元数据 JSON 经过 AES-256-GCM 认证加密后的密文（base64 编码）。GCM 模式自带认证标签，解密时自动校验篡改。这条扩展属性存在文件的 inode 里，不占用数据块空间，`cat` 看不到，`ls` 看不到。

- **`user.checksum`**：key 叫 "user.checksum"，value 是原始明文元数据 JSON 的 SHA-256 哈希值（明文存储，不加密）。用途是快速验证——解密后算一遍 SHA-256，跟这个值对比，一致就说明数据没损坏没被篡改。

### 2. inode 扩展属性是什么？

inode 是文件系统为每个文件分配的数据结构，存文件元信息。扩展属性就是这个结构里的一个附加存储区，可以放任意键值对。

对比理解：

| 概念 | 类比 |
|------|------|
| 数据块区 | 书的正文 |
| inode 基本字段（权限、时间） | 书的版权页 |
| xattr 扩展属性 | 藏在书脊夹层里的一张加密纸条 |

翻书看不到纸条，撕开封皮才能发现。用户 `cat`/`ls` 就是翻书，`getfattr` 才是撕开封皮。

### 3. 解密后还是建内存索引？

**是的，一模一样。** xattr 只是换了"元数据存哪里"，后端启动后读取 → 解密 → 构建 `files` dict 这个流程没有任何变化。内存索引的形态、查询方式、给 API 返回的格式，跟 `.meta.json` 方案完全一致。

唯一的区别就是读取来源从"解析同目录下的 JSON 文件"变成了"从 inode 里取 xattr 再解密"。
